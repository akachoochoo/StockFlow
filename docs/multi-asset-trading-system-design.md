## 1. 전략 선정 배경

### 1.1 검토한 옵션

| 옵션 | 평가 |
|------|------|
| ① HFT (고빈도 매매) | 개인 접근 불가. 코로케이션, FPGA, 시장조성자 자격 등 기관급 인프라 필요. 200ms 레이턴시 핸디캡으로 체결 우선순위 항상 뒤로 밀림 |
| ② 세븐 스플릿 자동화 | **개인에게 가장 합리적**. 단순 룰, 명시적 가정, 검증 가능. 알고리즘 50줄 |
| ③ AI가 일단위 파라미터 튜닝 | 매력적이지만 과최적화 위험. 일관성 깨뜨림 |
| **③' AI 차단기로 제한 적용** | **②의 안전장치로 추가 - 최종 선택** |

### 1.2 LLM 자율 매매 시스템의 한계

K-Agent Alpha (31개 LLM 에이전트), PRISM-INSIGHT (14개 에이전트) 등 사례 분석 결과:

- **상관된 환각**: 같은 학습 데이터 기반 LLM 여러 개를 엮어도 독립 검증이 아닌 합의된 환각 발생
- **시장은 비정상(non-stationary) 시스템**: 백테스트 +244%가 미래 보장 안 함
- **샘플 부족**: 1일 1회 의사결정이면 연 250 데이터 포인트 미만, 통계적 유의성 확보 어려움
- **Reflexivity**: 유사 시스템 증가 시 알파 소멸, 음의 알파 가능성

### 1.3 최종 전략

**세븐 스플릿 + AI 차단기 (Bounded Autonomy)**

- 메인 로직: 단순 룰 기반 분할 매수
- AI 역할: 시장 국면 판단 → 신규 진입 정지/축소만
- AI는 **파라미터 튜닝 X, 종목 선정 X, 매매 결정 X**
- 룰 기반과 AI 판단이 충돌 시 **보수적인 쪽 우선**

## 2. 시스템 적용 자산

### 2.1 자산별 특성 비교

| 자산 | 우상향 가정 | 변동성 | 거래 시간 | 비중 권장 |
|------|------------|--------|----------|----------|
| **KR 주식** | 중간 (개별주 위험) | 중간 | 9:00~15:30 KST | 30~40% |
| **US 주식** | 강함 (S&P500 100년 검증) | 낮음 | 23:30~06:00 KST | 30~40% |
| **BTC** | 약함 (15년, 80% DD 4회) | 매우 높음 (주식의 3~5배) | 24/7 | 5~10% |

### 2.2 자산별 파라미터

#### KR 주식
- **분할 간격**: 7%
- **분할 개수**: 7개
- **트리거**: 종가 기준
- **종목 선정**: 시총 상위, KOSPI 200 편입, 배당 지속
- **권장**: 인덱스 ETF (KODEX 200) 우선
- **차단기 신호**: VIX, 원/달러 환율, 외인 순매도 연속일, KOSPI 갭 하락

#### US 주식
- **분할 간격**: 8~10% (한국보다 변동성 낮음)
- **분할 개수**: 5~7개
- **트리거**: 종가 기준 (한국 시간 새벽)
- **권장**: S&P500 ETF, 우량주
- **고려사항**: 환율 리스크, 양도세 22%(기본공제 250만 원)
- **차단기 신호**: VIX 30+, MOVE 지수, 10년물 금리 급등, 연준 회의

#### BTC
- **분할 간격**: 15~20% (변동성이 주식의 3~5배)
- **분할 개수**: 5개 또는 시간 DCA
- **트리거**: UTC 기준 시간 분할 (종가 개념 없음)
- **비중 제한**: 포트폴리오 5~10%
- **차단기 신호**: 펀딩비 극단치, 거래소 유입량 급증, 김치 프리미엄, ETF 자금 유출, DXY

### 2.3 자본 배분 원칙

```
예시 배분:
KR 40% + US 40% + BTC 10% + 현금 10%
```

- **자산별 자본 배분을 먼저 고정**
- AI 차단기가 한 자산 진입을 정지해도 **다른 자산은 독립 운영**
- 같은 신호로 모든 자산 차단하면 분산 효과 소멸

## 3. 아키텍처 설계

### 3.1 핵심 추상화 (도메인 모델)

코드 작성 전에 5개 개념 정의:

| 개념 | 역할 |
|------|------|
| **Asset** | 거래 대상. 종목 코드, 자산 클래스, 거래소, 통화, 최소 단위 |
| **MarketSession** | 거래 가능 시간. "지금 거래 가능?", "다음 종가는 언제?" 답변 |
| **SplitStrategy** | 분할 매수 전략. 개수, 간격, 트리거 조건, 비중 |
| **CircuitBreaker** | 차단기. 신호 입력, 발동 조건, 발동 시 행동 |
| **Portfolio** | 자본 배분. 목표/현재 비중, 리밸런싱, 리스크 한도 |

### 3.2 레이어 아키텍처 (헥사고날)

```
┌─────────────────────────────────────────────┐
│           Application Layer                  │
│  (Orchestrator: 하루 1회 실행 진입점)         │
└─────────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────────┐
│           Domain Layer (자산 무관)            │
│  - SplitStrategy 로직                        │
│  - CircuitBreaker 평가 로직                   │
│  - Portfolio 리밸런싱 로직                    │
│  - Order 생성 로직                           │
└─────────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────────┐
│      Ports (인터페이스 정의)                  │
│  - MarketDataPort (시세 조회)                 │
│  - BrokerPort (주문 실행)                    │
│  - SignalPort (차단기 신호)                  │
└─────────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────────┐
│         Adapters (자산별 구현)                │
│  - KIS_Adapter (KR 주식)                    │
│  - IBKR_Adapter or Tiger_Adapter (US 주식)  │
│  - Binance_Adapter / Upbit_Adapter (BTC)    │
└─────────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────────┐
│      Infrastructure (DB, 로깅, 알림)          │
└─────────────────────────────────────────────┘
```

**이점**: 도메인 로직 한 번 작성 → 세 자산 모두 적용. 새 자산 추가 시 어댑터만 추가.

### 3.3 데이터 스키마

```sql
-- 핵심 테이블
assets               -- 거래 대상 마스터
positions            -- 현재 보유 (자산, 수량, 평단가, 분할 차수)
split_plans          -- 종목별 분할 계획 (목표가, 비중, 실행 여부)
orders               -- 모든 주문 이력 (요청/체결/실패)
signals              -- AI 차단기 신호 이력 (시점, 종류, 값, 발동 여부)
decisions            -- 매일의 의사결정 로그 (왜 샀는지/안 샀는지)
portfolio_snapshots  -- 일별 포트폴리오 스냅샷
```

**`decisions` 테이블이 가장 중요**: 6개월 뒤 디버깅을 위해 결정 시점 입력값 전체를 JSON으로 저장.

### 3.4 차단기 신호 파이프라인

```
SignalCollector (수집)
  ├─ MacroSignal (VIX, 환율, 금리)
  ├─ MarketSignal (KOSPI, S&P, BTC 변동성)
  └─ AssetSpecificSignal (외인 수급, 펀딩비 등)
        ↓
SignalEvaluator (평가)
  ├─ 자산별 임계치 체크 (룰 기반)
  └─ AI 판단 (선택적, 차단기 역할만)
        ↓
CircuitBreakerDecision
  ├─ NORMAL    (정상 운영)
  ├─ CAUTION   (신규 진입 50% 축소)
  ├─ HALT      (신규 진입 정지)
  └─ EMERGENCY (포지션 축소)
```

**AI 개입 지점은 단 하나**: SignalEvaluator의 "이 신호 조합이 평소와 다른가?" 판단. 매수 종목 선정이나 파라미터 튜닝엔 절대 개입 안 함.

**룰 기반과 AI 병행**: AI가 NORMAL이라도 룰 기반(VIX 40+)이 HALT면 HALT 우선.

### 3.5 인터페이스 정의 (시작점)

```python
class BrokerPort(Protocol):
    def get_balance(self) -> Balance: ...
    def get_positions(self) -> list[Position]: ...
    def place_order(self, order: Order) -> OrderResult: ...
    def cancel_order(self, order_id: str) -> bool: ...

class MarketDataPort(Protocol):
    def get_current_price(self, asset: Asset) -> Price: ...
    def get_ohlcv(self, asset: Asset, period: str) -> OHLCV: ...

class SignalPort(Protocol):
    def collect(self) -> list[Signal]: ...
```

도메인 로직이 인터페이스만 사용 → KIS, IBKR, Binance 갈아끼우기 가능. **테스트 시 Mock 구현체로 백테스트 그대로 실행**.

### 3.6 운영 안전장치 (필수)

| 항목 | 설명 |
|------|------|
| **Idempotency** | 동일 신호 재실행 시 중복 주문 방지. 모든 주문에 고유 ID + 중복 체크 |
| **Kill Switch** | 환경변수 하나로 모든 거래 즉시 중단 |
| **Reconciliation** | 매일 시스템 DB 포지션 vs 브로커 실제 포지션 대조. 불일치 알림 |
| **Observability** | 의사결정/주문/신호 로그 + 텔레그램 일일 요약 |
| **Secret Management** | API 키 환경변수/Vault 관리. 코드 하드코딩 금지 |

## 4. 백테스트 전략

### 4.1 백테스트의 본질

> 백테스트는 "과거에 잘됐다" 외에 아무것도 증명하지 않음. 그러나 **명백히 망가진 전략을 미리 거르는** 필수 단계.

### 4.2 피해야 할 함정

| 함정 | 내용 |
|------|------|
| **Look-ahead bias** | T일 의사결정에 T일 종가 사용 금지. T-1까지 데이터만 |
| **Survivorship bias** | 현재 상장 종목만 사용 시 망한 회사 누락. 인덱스 ETF 백테스트가 안전 |
| **Data snooping** | 같은 데이터로 100번 파라미터 변경 시 우연 적합 발생 |
| **거래 비용 무시** | 수수료, 세금, 슬리피지 빼면 대부분 전략이 수익 나 보임 |

### 4.3 3단계 백테스트 설계

#### Stage 1: 인-샘플 (60~70%)
- 학습/튜닝용 (예: 2015~2022)
- 여기서 잘 나오는 건 당연. **의미 없음**.

#### Stage 2: 아웃-오브-샘플 (30~40%)
- 단 한 번만 테스트 (예: 2023~2025)
- IS 대비 비슷하면 OK, 크게 떨어지면 과최적화
- **결과 보고 파라미터 재조정 금지** → 그 순간 OOS가 IS가 됨

#### Stage 3: 워크-포워드
- 2년 학습 → 6개월 테스트 → 6개월 슬라이딩
- 시간에 따른 시장 변화 반영
- 세븐 스플릿은 파라미터 단순해서 풀버전까진 불필요

### 4.4 평가 지표 (수익률만 보지 않기)

| 지표 | 의미 | 목표 |
|------|------|------|
| **CAGR** | 연복리수익률 | 벤치마크 대비 + |
| **MDD** | 최대 낙폭 | 수익률보다 중요. -50% 회복 = +100% 필요 |
| **Sharpe** | 변동성 대비 수익 | 1.0+ |
| **Calmar** | CAGR / MDD | 0.5+ |
| **Win Rate × Avg Win/Loss** | 승률과 평균 수익/손실 비율 | 세븐 스플릿은 승률↑ 비율↓ 패턴 |
| **벤치마크 초과수익** | KOSPI/S&P500 대비 | 못 이기면 인덱스 매수가 답 |

### 4.5 데이터 소스

| 시장 | 무료 | 유료 |
|------|------|------|
| **KR** | pykrx, FinanceDataReader, KIS API | - |
| **US** | yfinance, Alpha Vantage 무료 티어 | Polygon.io |
| **BTC** | Binance API, ccxt, CryptoCompare | - |
| **거시** | FRED API (미국), 한국은행 ECOS | - |

### 4.6 백테스트 프레임워크

| 라이브러리 | 특징 |
|-----------|------|
| **backtrader** | 한국 사용자 많음, 문서 풍부 |
| **vectorbt** | 빠르고 그리드 서치 강함, 학습 곡선 가파름 |
| **zipline-reloaded** | Quantopian 후속, 견고 |

**핵심**: 백테스트 코드와 실거래 코드가 **동일한 도메인 로직 공유**해야 함. Mock Broker 패턴 활용.

### 4.7 페이퍼 트레이딩 (백테스트 → 실거래 다리)

- 백테스트 양호해도 **3개월 이상 페이퍼 트레이딩** 필수
- 검증 항목: 실시간 데이터 지연/누락, API 에러, 가용 정보 한계, 재시작 복구
- **페이퍼 결과가 백테스트의 50% 이하 → look-ahead bias 의심**

## 6. 라즈베리파이 운영 가이드

### 6.1 결론: 충분히 가능, 오히려 추천

세븐 스플릿은 계산 부하 거의 없음. 라즈베리파이 4(4GB)도 충분.

### 6.2 비용 (라즈베리파이 5 8GB 기준)

- 본체: 약 12만원
- 케이스 + SD카드 + 전원: 3~5만원
- **초기 합계: 15~17만원**
- 소비전력: 평균 5~8W
- **전기세: 월 500~1000원** (24시간 가동)

**5년 운영 시 클라우드 대비 50만원+ 절약**

### 6.3 라즈베리파이의 진짜 이점

1. **물리적 제어권**: 클라우드 업체 정책 변경/중단에서 자유
2. **인터넷 끊김 대응**: UPS + LTE 백업 가능
3. **데이터 프라이버시**: 거래 기록 외부 유출 없음
4. **학습 가치**: Linux, 네트워크, 모니터링 전반

### 6.4 단점과 대응

| 단점 | 대응 |
|------|------|
| **SD카드 수명** (24/7 시 1~2년) | SSD 부팅, 로그는 외부 DB |
| **정전** | 미니 UPS (5만원) 또는 보조배터리 |
| **인터넷 끊김** | LTE/5G USB 동글 백업, 또는 "네트워크 불안정 시 거래 정지" 차단기 |
| **하드웨어 고장** | 백업 라즈베리파이 1대 추가, SD 이미지 복제 (30분 내 교체) |
| **시간 동기화** | NTP 필수 |

### 6.5 권장 구성: 하이브리드

```
┌─────────────────────────────────┐
│   라즈베리파이 5 (메인)           │
│   - 거래 시스템 코어              │
│   - SQLite DB (로컬)             │
│   - SSD 부팅                     │
└─────────────────────────────────┘
            ↓ (백업/모니터링)
┌─────────────────────────────────┐
│   클라우드 (보조)                 │
│   - 로그 백업 (Oracle Free Tier) │
│   - 텔레그램 알림 봇              │
│   - 헬스체크 (외부에서 핑)        │
└─────────────────────────────────┘
```

**연 운영비**: 약 1~2만원 (전기세만)
**초기 비용**: 약 25만원 (파이 2대 + 주변기기)

### 6.6 외부 모니터링 (필수)

라즈베리파이가 죽으면 자체 알림 불가. 외부 모니터링 필수:

- **UptimeRobot** (무료): 5분마다 외부 핑, 응답 없으면 텔레그램 알림
- **Healthcheck.io** (무료): 시스템이 주기적으로 "살아있다" 신호 송신, 미수신 시 알림

→ 시스템 다운 5~15분 내 감지

### 6.7 비용 시나리오 종합

| 시나리오 | 초기 | 월 비용 | 연 비용 |
|---------|------|---------|---------|
| **최소** (파이 + 무료 티어) | 25만원 | 1천원 + LLM $1~2 | 3~5만원 |
| **중간** (Oracle Free Tier) | 0 | LLM $1~5 | 3~10만원 |
| **편의** (AWS 등) | 0 | $20 | 30만원 |

**추천 경로**: 처음 6개월 로컬 PC/노트북 → 안정화 후 라즈베리파이 + Oracle Free Tier 이전

## 8. 핵심 원칙 요약

### 8.1 설계 원칙

1. **단순함이 알파**: 복잡한 알고리즘이 아닌, 단순한 룰의 일관된 실행
2. **AI는 보조 안전장치**: 메인 의사결정에 절대 개입 금지
3. **자산별 독립**: 공통 시스템 + 자산별 파라미터 + 독립 차단기
4. **인터페이스 우선**: 어댑터 교체 가능한 구조
5. **로그가 자산**: 의사결정 시점 입력값 전체 보존

### 8.2 운영 원칙

1. **점진적 확장**: KR → US → BTC 순서, 각 단계 1개월+ 검증
2. **Kill Switch 필수**: 언제든 즉시 중단 가능
3. **외부 모니터링**: 시스템이 죽었음을 외부에서 감지
4. **이중화**: 백업 하드웨어 + 백업 네트워크
5. **재무적 한계**: BTC는 포트폴리오 5~10% 이내

### 8.3 검증 원칙

1. **백테스트 ≠ 미래**: 망가진 전략 거르는 용도일 뿐
2. **OOS 한 번만**: 결과 보고 재조정 금지
3. **페이퍼 트레이딩 3개월+**: 백테스트와 결과 비교
4. **벤치마크 초과수익**: KOSPI/S&P500 못 이기면 인덱스 매수

### 8.4 실계좌 시스템의 진실

> **비용 절약보다 안정성이 100배 중요.**
> 한 번 시스템 다운으로 손절 못 해서 입는 손실이 5년치 클라우드 비용보다 큼.
>
> **개인 투자의 진짜 적은 시장이 아니라 자신의 손절 충동.**
> 자동화의 본질은 "더 똑똑한 결정"이 아니라 "감정 개입 차단"이다.
