### 1.2 학습 목표 명확화 (사용자 §2.1 박제)

#### 1.2.1 패러다임 비교 (가치 → 기술적)

Phase 0.8 의 핵심 = **매수 패러다임 차원 변경**:

| 차원 | Phase 0 / 0.5 / 0.7 | Phase 0.8 |
|---|---|---|
| 매수 트리거 | `PriceDropStrategy` — `avg_price` 대비 N% 하락 (가치) | `SupportLevelStrategy` — 보조 지표 기반 지지선 도달 (기술적) |
| 의사결정 변수 | 평균 단가 + 현재가 + 임계값 | 가격 + MA / BB / RSI 등 보조 지표 |
| 슬롯 의미 | 차수 번호 (1~7, 누적) | 지지선 종류 (1~7, 매핑) |
| 박영옥 원전 정신 | 가치 투자 (분할 매수) | 기술적 분석 (지지선) |

#### 1.2.2 박영옥 원전 정신 폐기 아님

`PriceDropStrategy` (Phase 0~0.7) 는 박영옥 세븐스플릿의 핵심 정신
(분할 매수 + 평단 관리). **Phase 0.8 = 폐기 아닌 비교** — 두 패러다임
모두 유지:

- yaml `buy_strategy: "price_drop"` → 기존 strategy
- yaml `buy_strategy: "support_level"` → Phase 0.8 신규 strategy
- 둘 다 회귀 invariant 보존 (`PriceDropStrategy` 변경 zero)

→ Phase 0.7.3 baseline (PriceDropStrategy) 와 Phase 0.8 (SupportLevelStrategy)
는 같은 환경 (자산 + 자본 배분 + 매도 + 재진입) 에서 매수 패러다임만
변경한 직접 비교.

#### 2.2.3 "이탈" 정의 + 우상향 전제

**"이탈" 정의 (Phase 0.8.1 단순화)**:
- `current < trigger` (strict less than)
- equal 케이스 (`current == trigger`) 트리거 안 함
- tolerance / buffer 미적용

**Phase 0.8.x 후속 정교화 가능** (본 박제 이후 별도 결정 라운드):
- 옵션 C: 하향 돌파 (어제 위 → 오늘 아래)
- 옵션 D: 슬롯별 차등 tolerance (예: MA5 -1%, MA20 -3%)
- 슬롯 5 "돌파 후 되돌림" 패턴 인식

**우상향 전제 (사용자 명시 §2.1 박제)**:
- 슬롯 1 first-buy 의 코드 필터 = `split_level == 0` 만 (지표 없음).
- 우상향 확인 = **종목 선정 단계의 분석 전제** — 타겟 종목은 우상향
  할 것으로 분석되었다는 가정이 붙은 상태에서 시스템에 등록.
- 즉 Phase 0.8 의 SupportLevelStrategy 는 "우상향 종목의 일시적 이탈"
  을 매수 시점으로 본다 (가치 투자 정신 + 기술적 분석 결합).
- **코드 레벨 우상향 필터 (예: `current > MA200`) 도입 안 함** —
  yaml 종목 등록 자체가 우상향 분석 통과의 증거.
- Phase 1+ 실거래 진입 시 "우상향 분석" 의 형식화 (예: 명시적
  체크리스트 / 사람 승인 게이트) 검토 가능.

#### 2.2.5 PriceDropStrategy 와의 패턴 차이 (의도된 미묘한 차이)

| 항목 | PriceDropStrategy (Phase 0~0.7) | SupportLevelStrategy (Phase 0.8) |
|---|---|---|
| 비교 연산자 | `current ≤ trigger` (≤, equal 포함) | `current < trigger` (strict <) |
| 의미 | "임계 도달 시 매수" — 가치 투자 (분할 매수 포함) | "지지선 이탈 시 매수" — 기술적 (이탈 시점) |
| equal 케이스 | 트리거 (포함) | 트리거 안 함 (제외) |

**미묘한 차이의 의도**:
- 가치 투자 (PriceDropStrategy) = "임계 도달 = 매수 기회" → equal 포함
  자연스러움
- 기술적 분석 (SupportLevelStrategy) = "이탈 = 추세 약화 신호" → equal
  은 지지선 유지 (이탈 아님)
- **본질적 패러다임 차이의 코드 표현** (CLAUDE.md §13.3 "친절한 추가
  금지" 정합 — 의도적 차이)

### 4.3 결정 β = reentry policy 주입 무 (각 슬롯 자체 indicator 트리거)

#### 4.3.1 옵션 비교

| 옵션 | 채택 | 근거 |
|---|---|---|
| (β-1) `ReentryPriceStrategyPort` 주입 (PriceDropStrategy 패턴 그대로) — 슬롯 트리거 = `last_exit_price * (1 - drop_threshold_pct)` | 거부 | SupportLevelStrategy 의 트리거 = indicator 값. last_exit_price 기반 anchor 와 의미 다름 — 매수 패러다임 차원 변경 (§1.2.1) 의 본질 |
| **(β-2) reentry 주입 무 — slot 트리거 = indicator condition** | **채택** | 슬롯 의미 정합 (§2.2.1) — 슬롯 = 지지선 종류, 트리거 조건 = `current < indicator_value`. cooldown 무 — 매도 후 즉시 재트리거 가능 (slot 이 indicator 조건 충족 시) |

#### 4.3.2 §1.7 baseline 의 "재진입 정책 F" 정밀화

§1.7 baseline 표 ("재진입 정책 = F (HybridTimeBasedReentry, cooldown=60)
| 동일") 의 "동일" 은 **PriceDropStrategy 와 SupportLevelStrategy 에서
다르게 적용됨**:

| 전략 | 재진입 트리거 | cooldown |
|---|---|---|
| PriceDropStrategy (baseline) | `last_exit_price * (1 - drop%)` (anchored) | 60 일 |
| SupportLevelStrategy (Phase 0.8.1) | `current < indicator_value` (indicator-based) | **무** (Phase 0.8.1 단순화) |

- PriceDropStrategy 는 yaml `reentry_strategy: hybrid` 그대로 (Phase
  0.7.3 baseline)
- SupportLevelStrategy 는 reentry 정책 비주입 — 슬롯 트리거가 자체
  indicator 조건 + cooldown 무
- **변수 통제 정합**: 매수 패러다임 차원만 변경 (§1.2). 재진입 매커니즘
  은 본질적으로 다른 차원이므로 "동일 매커니즘" 보존이 아닌 "각
  패러다임 자연스러운 매커니즘" 채택

#### 4.3.3 cooldown 무의 trade-off

| 항목 | 영향 |
|---|---|
| 자본 회전 (H1) | ↑ — 매도 후 즉시 재트리거 가능 → turnover ↑ 가능성 |
| Whipsaw 위험 | ↑ — MA 이탈 직후 회복 시 매도 / 즉시 재매수 사이클 가능 |
| Phase 0.8.x 후속 | cooldown 도입 검토 가능 (옵션 — 별도 결정 라운드) |

박제: Phase 0.8.1 = cooldown 무 default. 결과 분석 시 whipsaw 빈도
지표화 → Phase 0.8.x 에서 cooldown 추가 결정 라운드 진입 가능.

#### 4.3.4 슬롯 1 first-buy 처리

슬롯 1 = first-buy 전용 (§2.2.1):
- `position is None` 또는 `position.split_level == 0` 시 트리거
- indicator 무 — 우상향 전제 (§2.2.3) 자산의 진입점
- 트리거 조건 = always true (slot_number == 1 EMPTY + split_level == 0)
- 매도 후 split_level == 0 으로 돌아오면 슬롯 1 재트리거 가능

  = 60+ 거래일
- 각 테스트는 closes pattern 만 다르게 (예: 단조 증가 / 단조 감소 /
  슬롯별 트리거 시나리오)

### 4.6 SupportLevelStrategy 알고리즘 박제

```
1. Preconditions
   - position.asset == current_price.asset
   - balance.cash.currency == asset.currency
   - config.per_split_amount.currency == asset.currency
   - ohlcv_history is sorted ascending (caller responsibility)

2. max_split_per_day guard (PriceDropStrategy 동일)
   - count today's FILLED slots vs config.max_split_per_day

3. max_split_count guard
   - position.split_level >= config.max_split_count → STRATEGY_NO_BUY

4. Determine candidate EMPTY slot_numbers
   - position is None → all 1..config.max_split_count
   - position exists → [s.slot_number for s in empty_slots]
   - exclude excluded_slot_numbers

5. Slot 1 first-buy bypass
   - if 1 in candidate and (position is None or split_level == 0)
   - → return BuyDecision(slot_number=1, ...)

6. Slots 2~5 indicator evaluation (Phase 0.8.1)
   - closes = [bar.close for bar in ohlcv_history]
   - For each candidate slot in [2, 3, 4, 5]:
     - 2: indicator = calculate_sma(closes, 5)
     - 3: indicator = calculate_sma(closes, 10)
     - 4: indicator = calculate_sma(closes, 20)
     - 5: indicator = find_recent_high(closes, 60)
   - if indicator is None → none_count++ (insufficient data)
   - if current_price.value < indicator → triggers.append((slot, indicator))

7. Skip reasons
   - if no triggers and none_count == evaluated_count → INSUFFICIENT_HISTORICAL_DATA
   - if no triggers but data fine → ALL_SLOTS_EMPTY_NO_TRIGGER
   - else: smallest slot_number wins

8. Quantity / price + balance check + BuyDecision
   - target_price = asset.round_to_tick(current_price.value)
   - target_quantity = floor(per_split_amount / target_price, lot_size)
   - target_quantity <= 0 → QUANTITY_TOO_SMALL
   - balance.cash.amount < actual_cost → INSUFFICIENT_BALANCE
```
