## 1. Context

종목을 실제로 거래하려면 **두 곳**이 일치해야 했다:

1. `config/strategies*.yaml` — 종목별 매수/매도/재진입 전략 + 파라미터 (데이터, YAML).
2. `src/cli/composition.py` 의 `_ASSET_FACTORIES` — 코드 → `Asset` 값 객체(`exchange` / `market` / `asset_class` / `currency` / `tick_size` / `lot_size` / `listed_at`) 팩토리 레지스트리. Phase 0 기준 **9 종 하드코딩** (`kodex200()` 등).

`asset_from_code()` 는 레지스트리에 없는 코드에 `KeyError` 를 던졌다 (*"new codes need composition.py update"*). 즉 **종목 1 개 추가 = YAML 편집 + Python 소스 편집** 두 곳 — 운영 단계에서 종목 유니버스가 자주 바뀌면 번거롭고, 소스 편집(또는 code-gen)은 취약하다.

이 하드코딩은 **Phase 0 의 의도적 임시방편**이었다. 근거가 코드에 박제되어 있다:

- `composition.py:739-740` — *"Hardcoded here so the CLI default works without a config file. **When Phase 1 adds multiple assets this graduates to a YAML lookup.**"*
- `yaml_strategy_config_loader.py` docstring — *"these KRX-specific fields stay **hardcoded until Phase 1+** multi-exchange arrives."*

Phase 0~0.11 은 고정된 소수 종목(≤9)으로 백테스트했고, 종목은 ADR 1 개씩(예: ADR 0005 §1.6.2 "박제 종목") 신중히 추가했다 — 마찰이 의도된 연구 단계 규율. 그러나 Phase 1.1(실거래) 진입 후 운영 종목 관리 편의가 사용자 요구로 등장.

**결정 라운드 (인터랙티브, 2026-05-23)**: (a) 데이터 주도 vs code-gen → **데이터 주도 승인**, (b) pykrx 교차검증으로 오류 최소화 **승인**, (c) `composition.py` fallback **아키텍처 변경 승인**.

---

## 2. Decision

Phase 0 하드코딩을 **유지한 채**, 그 위에 데이터 주도 레지스트리를 **additive overlay** 로 얹는다. 4 개 산출물:

### 2.1 `config/assets.yaml` (신규 데이터 파일)

종목 메타데이터 레지스트리. `version: "1.0"` + `assets:` map (코드 → 메타). 필드:

| 필드 | 필수 | 기본 | 의미 |
|------|------|------|------|
| `name` | ✓ | — | 종목명 |
| `market` | ✓ | — | `KOSPI` / `KOSDAQ` |
| `asset_class` | ✓ | — | `KR_ETF` / `KR_STOCK` |
| `listed_at` | ✓ | — | 상장일 (5년 백테스트 가용성·tradeable 기준) |
| `tick_size` | — | KR_ETF=5 / KR_STOCK=1 | 호가단위 |
| `lot_size` | — | 1 | 매매단위 |
| `exchange` | — | `KRX` | 거래소 |
| `currency` | — | `KRW` | 통화 |
| `delisted_at` | — | `None` | 상장폐지일 |

### 2.2 `src/infrastructure/yaml_asset_loader.py` (신규 로더)

`load_asset_registry(path) -> dict[str, Asset]`. `yaml_strategy_config_loader` 와 동형:
- strict `extra='forbid'` pydantic — 오타 = `ValidationError` (silent default 금지, CLAUDE.md §13.3).
- YAML float → `Decimal(str(v))` (CLAUDE.md §2.3).
- `tick_size` 생략 시 `asset_class` 기본값 (KR_STOCK=1 = `round_to_tick` helper placeholder, ADR 0005 §3.3.1 팩토리와 동일).
- **빈 `assets: {}` / 없는 파일 → `{}`** (회귀 안전 — fallback 미존재 시 Phase 0 하드코딩-only 와 동일 동작).

### 2.3 `composition.asset_from_code` (additive 변경)

```
asset_from_code(code, registry_path=None) -> Asset
  1. _ASSET_FACTORIES (하드코딩 9 종) 우선 — byte-identical, 회귀 invariant.
  2. miss → config/assets.yaml fallback (load_asset_registry).
  3. 둘 다 miss → KeyError (메시지에 하드코딩 + yaml 코드 목록).
```

- `registry_path` = optional (기본 `<repo>/config/assets.yaml`, `__file__` 기준 해석 → cwd 무관). 기존 호출부 6 곳 (`main.py`) **변경 zero** (단일 인자 호출 그대로).
- 기존 9 팩토리 **무손상** — `test_unknown_code_raises_key_error` (999999→KeyError) 계약 보존.

### 2.4 `scripts/manage_strategies.py` (신규 관리 CLI)

10 명령: `list` / `show` / `validate` / `add` / `remove` / `enable` / `disable` / `set` / `new` / `diff`. argparse(stdlib), `main(argv)` 진입.

#### 2.4.1 검증 재사용 (스키마 재구현 zero)

`validate` + 모든 mutating 명령은 **실제 로더**(`load_strategy_config` / `load_asset_registry`)를 temp-file 로 호출해 검증 → drift 불가. **쓰기 전 검증** = 실패 시 어떤 파일도 건드리지 않음(부분 쓰기 방지). `cross_check` = strategies 의 모든 코드가 (하드코딩 ∪ assets.yaml) 에 메타데이터를 갖는지 확인.

#### 2.4.2 pykrx 교차검증 (`add`, 기본 ON)

best-effort + graceful (네트워크 단절/미설치/엔드포인트 실패 → 경고 후 진행, never raise). 종목명 자동 채움 + 시장/데이터 가용성 교차 확인. **`listed_at` 은 pykrx 가 아니라 사용자 입력 + 경고**로 다룸 — 법적 상장일은 KRX/DART 공식 자료로 확인 (verify_phase_0_9_assets.py §1.7.4 규율 정합, pykrx 는 데이터 시작일 proxy 로 soft check). 검증 로직은 주입식 lookup 으로 분리해 단위 테스트(네트워크 zero).

#### 2.4.3 정책 균일성 보존 (ADR 0003 §7.3 정합)

`add` 는 기존 종목(template)에서 전략 TYPE + 파라미터를 상속 → 기본(strict 균일) 로더 통과. `set --code` 가 균일성을 깨면 로더가 거부하고 파일 미변경 (`allow_per_asset_params: true` 필요 안내).

### 2.5 inner-ring 영향 zero

- `src/domain/models.py` `Asset` 모델 **변경 zero** (로더가 기존 모델로 생성 — 동일 pydantic 검증 통과).
- Port 시그니처 **변경 zero**.
- 변경된 inner 코드 = `composition.asset_from_code` (composition root, additive optional arg + fallback) **단 1 함수**.

---

## 3. Drivers

- 운영 단계 종목 유니버스 변동 = 코드 수정 없이 **데이터 편집 1 회**로 (사용자 요구).
- `composition.py:740` 가 예고한 graduation 의 적기 = Phase 1.1.
- 실머니 시스템 — money-critical 메타데이터(`tick_size` / `listed_at`)는 잘못되면 호가 오류·백테스트 가용성 오판. 데이터화하되 **검증을 잃지 않아야** 함.
- code-gen(소스 텍스트 조작)은 취약 + 생성/수기 코드 혼재 → 회피.

---

## 4. Alternatives Considered

1. **code-gen into composition.py** (`add` 가 팩토리 함수 + dict 줄을 소스에 삽입) — 거부. 텍스트 조작 취약 + 생성/수기 혼재. 데이터 주도가 더 단순·안전.
2. **9 팩토리 전부 assets.yaml 로 즉시 이관** — 보류. `market` / `tick_size`(5 vs 1) / `listed_at` 정확 보존 필요 + ADR 인용 "박제 종목" → 회귀 risk. additive overlay(하드코딩 유지)가 회귀 zero. 통합은 후속(§7).
3. **ruamel.yaml 로 주석 보존** — 거부. 새 외부 의존성(CLAUDE.md §0.3 승인 대상). pyyaml + 자동 생성 헤더 채택 (사용자 승인 trade-off, 기존 주석 손실 허용).
4. **pykrx 로 `listed_at` 자동 확정** — 거부. 법적 상장일은 KRX/DART 공식 자료 규율(ADR 0005 §1.7.4). pykrx 는 데이터 가용성 proxy + soft 경고만.
5. **click CLI** (프로젝트 main CLI 와 일관) — 거부. 관리 스크립트 자족성 위해 argparse(stdlib). `scripts/` 기존 도구들과 정합.
6. **assets.yaml 검증 스키마 자체 구현** — 거부. 실제 로더 재사용(temp-file) → 단일 진실, drift zero.

---

## 5. Why (선택 근거)

데이터 주도 + additive overlay 는: (a) 종목 추가 = 데이터 편집 1 회(코드 0), (b) 기존 9 팩토리 무손상 → 회귀 zero, (c) `Asset` pydantic 검증을 그대로 통과해 타입·범위 안전성 유지, (d) 하드코딩 대비 잃는 "사람 검증 의례"를 pykrx 교차검증 + 경고로 부분 보전, (e) `composition.py:740` 의 원 설계 의도 이행. money-critical 현실(KIS/KRX 메타데이터)을 정직하게 다루면서(검증·경고) 운영 편의를 확보한다.

## 6. Consequences

**Positive**:
- 종목 추가 시 `composition.py` 수정 불필요 — 데이터 편집 + pykrx 검증.
- 회귀 zero: **2211 → 2266 tests (신규 55)**, ruff clean, mypy clean (변경 src 2 파일).
- 쓰기 전 검증 + cross_check = 잘못된 설정이 런타임(첫 체결)에 도달하기 전 차단.
- `composition.py:740` 예고 이행 — 설계 의도와 정합.

**Negative / 보류**:
- **두 source of truth** (하드코딩 9 + assets.yaml) — 일시적. §7 통합 후속.
- pyyaml 재작성 시 strategies/assets YAML 의 기존 주석 손실 (사용자 승인). mutating 명령이 경고 출력.
- pykrx 네트워크 의존 — graceful(경고 후 진행)이나 오프라인 시 교차검증 불가 → 수동 확인 안내.
- `remove` 는 strategies 만 정리, assets.yaml 메타데이터는 수동 정리(보수적 — 메타 보존).

## 7. Follow-ups

1. **9 팩토리 → assets.yaml 통합 마이그레이션** — ✅ **DONE (2026-05-23)**. `_ASSET_FACTORIES` 제거, 9 종 전부 `config/assets.yaml` 로 이관, `asset_from_code` = assets.yaml 단일 정본. byte-identical 검증 (스냅샷 before/after 9/9 일치). **서브 결정**: 9 개 named accessor (`kodex200()` 등) 는 **삭제 대신 thin wrapper 보존** (`return asset_from_code("CODE")`) — 5 개 테스트 파일이 이를 Asset 생성자로 사용 중이라 API 보존(인터페이스 유지, 구현 교체). 데이터 중복 zero(wrapper 는 값 미보유). 회귀: 2265 tests pass, ruff/mypy/namespace clean.
2. **KIS 어댑터 진입 시 tick/lot 실 KRX 규칙** — 현재 `tick_size` placeholder(ETF=5/STOCK=1, `round_to_tick` 가격대별 helper). KIS 어댑터(ADR 0012)가 실 시장 규칙 공급 시점에 재검토 (ADR 0005 §3.3.1).
3. **ADR 0012 종목 유니버스 결정과 정합** — Phase 1.1 실거래 종목 확정 시 본 CLI 로 assets.yaml 구성.
4. **pyproject 에 pykrx 반영 여부** — 현재 research/tooling only (memory `pykrx 설치됨`). 관리 스크립트가 운영 필수 도구가 되면 optional-dependencies(`dev` 또는 신규 `ops`) 반영 검토 — 외부 의존성 승인(CLAUDE.md §0.3).
