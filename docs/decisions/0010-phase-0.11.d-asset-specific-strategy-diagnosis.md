### 1.2 현재 구조의 단서 박제 (사전 진단 — 본 phase 가 정밀화 대상)

**증거 1 — CLAUDE.md §14 "작성 금지" 통합 목록**:
> "종목별 다른 정책 (자산별 다른 정책) — Phase 1+ (ADR 0003 §19.4 / ADR 0004 §7.4.2 보류)"

**증거 2 — CLAUDE.md §16.1 항목 #4 단일 sell strategy 가정 invariant**:
> "sell strategy 단일 가정 — `ProfitTargetSell` 단일 sell strategy 가정 유지. 손절 (StopLoss) 은 Phase 1 ADR 에서 sell strategy 추가 형태로 도입."

**증거 3 — `docs/multi-asset-trading-system-design.md` §2.2 + §2.3**:
설계 의도는 자산별 파라미터 분리 (KR 7%/7분할, US 8-10%/5-7분할, BTC 15-20%/5분할) + "AI 차단기가 한 자산 진입을 정지해도 다른 자산은 독립 운영". 그러나 *파라미터 자산별 차별화* ≠ *전략 객체 자산별 차별화*.

**증거 4 — Phase 0.7 ~ 0.9 회고 패턴**:
Phase 0.7.3 baseline (069500 + 132030 EQUAL) = *동일 전략 (PriceDropStrategy) 을 두 자산에 적용 + weight 만 다름*. ADR 0005 §9.6.2 "자산군 분산 = H3 충분 조건" 은 자산-weight 분산의 효과를 입증했을 뿐, 자산-전략 분산은 미검증 영역.

**증거 5 — Phase 0.11.a §8.1 한계**:
> "DGT 단독 069500 vs Phase 0.7.3 069500+132030 의 자산 1차원 차이 — 분산 효과의 분리 측정 불가."

→ 비교조차 *자산 = 전략* 짝짓기 단위로 못 함. 구조적 단서.

**증거 6 — `BacktestRunner` 의 `per_asset_strategy_overrides` 기존재 (Round 1 ITERATE Architect critical finding)**:

`src/application/backtest_runner.py:187` 에 **`per_asset_strategy_overrides: dict[str, SplitStrategyConfig] | None` 이미 존재** — 파라미터 차별화 경로가 backtest layer 에 *기존 구현*. `BacktestRunner` 가 자산별로 다른 `SplitStrategyConfig` 를 수용 가능.

**증거 7 — `AssetContext` 기존 구현 (CLAUDE.md §16.1 항목 #2 괴리)**:

`src/use_cases/asset_context.py:37-57` 의 `AssetContext` frozen dataclass 는 **이미 자산별 `strategy` + `config` + `sell_strategy` + `sell_config` 번들링**. CLAUDE.md §16.1 항목 #2 가 "AssetContext 기반 데이터 흐름 의식 (코드 추가 금지)" 으로 박제 — 그러나 실제 코드에는 `AssetContext` dataclass + `DailyOrchestrator` / `composition.py` 사용처 *이미 구현*. **CLAUDE.md §16.1 항목 #2 와 코드 현실 괴리 박제 의무** (Round 1 ITERATE Patch 2 + 11, 옵션 Z = §3 회고에 정정 권고만, 정정 commit 안 함).

**증거 8 — 정책 동일성 강제 지점**:

`src/cli/composition.py:230-243` 에서 모든 자산에 **동일 strategy 인스턴스 공유 주입** + `src/infrastructure/yaml_strategy_config_loader.py:157-201` 의 `_check_policy_uniformity` Pydantic validator 가 **정책 동일성을 yaml load 시점 강제**. 자산-전략 type 차별화의 차단 지점 = composition + validator 2 곳.

**잠정 결론 정정** (Round 1 ITERATE Patch 1, Architect critical finding 흡수):

현재 구조는 **3-layer 구조**:
- (a) Strategy *type* = **단일 공유** (composition.py:230-243 + `_check_policy_uniformity` 강제)
- (b) Strategy *config* (parameter) = **자산별 차별화 이미 가능** (`per_asset_strategy_overrides`, backtest_runner.py:187)
- (c) `AssetContext` dataclass = **이미 자산별 strategy + config + sell_strategy + sell_config 번들링 구조** (asset_context.py:37-57)

→ 원하는 구조 `{asset_i: (strategy_i, params_i)} for each i` 와의 거리는 **D3 후보별로 다름**: (i) Mapping = `per_asset_strategy_overrides` 일반화 (최소 변경) / (ii) AssetContext = composition 시점 공유 제약 해제만 필요 (`composition.py:232-243` 수정 + `_check_policy_uniformity` 완화) / (iii) Strategy Registry = renderer dispatch 와 본질 다름 (stateful position 변경 vs stateless read-only — renderer_registry.py 패턴 직접 정합 zero) / (iv) Portfolio composition = capital allocation (ADR 0003 §17) 과 결합 시 cascading 최대.

**이전 잠정 결론** ("multi-asset / single-strategy") 은 (a) layer 만 본 부정확 표현 — (b)/(c) layer 의 기존 구현 누락. 정정.

  - **(ii) D3 trade-off 표 + cascading 영향 surface 박제 commit hash 박제** — `docs/analysis/phase-0.11.d-coupling-model-candidates.md` commit hash 본 ADR §3 회고에 박제.
  - **(iii) ADR 0008 D11 trigger 결과 (DGT promote 권고 or archive 확정) 가 본 phase 의 D3 후보 식별에 미치는 영향 *positive / neutral / negative* 박제**:

### 1.4 Gates G1~G4 (success criterion, ralplan #26 박제 대상)

> 본 phase 는 *분석 phase 의 분석 phase* — Phase 0.11.a 의 "박제 primary, runner secondary" pattern 을 **극단까지 적용**. 모든 게이트가 박제 산출의 정합성으로만 정의됨. **실행 게이트 없음**.

- **G1 (PRIMARY)** — 현재 구조 진단 보고서 박제 (D1+D2 산출, 5 증거 + 변경 surface 표 + 객체 시그니처 dump).
- **G2 (PRIMARY)** — 자산-전략 결합 모델 후보 박제 (D3+D4 의 4+3 옵션 trade-off 표).
- **G3 (PRIMARY)** — ADR header + 회고 + supersede 시나리오 template 박제 (D5+D9).
- **G4 (PRIMARY)** — namespace CI + mypy strict (코드 변경 zero 이므로 0.11.a invariant 자동 보존) + D10 lifecycle 정의 명시.

**G2 가 INFORMATIONAL 강등 없음** — 본 phase 의 모든 산출은 박제 자체가 목적. Phase 0.11.a 의 G2 (DGT IRR baseline 비교) 같은 *실행 검증* 차원이 부재.

### 1.5 Risks (R1~Rn, ralplan #26 박제 대상)

- **R1 (HIGH)** — **진단 보고서가 박제 후 stale 되는 risk**. 본 phase 와 후속 결정 라운드 사이에 다른 phase (0.11.b/c, Phase 1) 가 코드를 변경하면 D2 의 변경 surface 가 즉시 stale. Mitigation: D10 staleness tripwire + 후속 phase 진입 시 cross-check 의무화.
- **R2 (HIGH)** — **후보 박제가 prematurely 결정으로 굳는 risk**. D3 (i)~(iv) 후보를 박제하면 후속 라운드 Critic 의 antithesis 공간이 좁아짐. Mitigation: §1.3 D3 의 "본 phase 는 채택 안 함 — 후보 박제 + trade-off 분석만" 문구를 ADR 본문에 invariant 로 박제.
- **R3 (MEDIUM)** — **Sell strategy 단일 가정 해제의 cascading risk**. CLAUDE.md §16.1 항목 #4 invariant 해제는 `OrderRequest` / `OrderResult` 시그니처, partial fill 처리, reconciliation 흐름 전반에 영향. Mitigation: D4 의 (a)~(c) 후보 각각에 대해 cascading 영향 surface 박제.
- **R4 (MEDIUM)** — **ADR 0008 (Phase 0.11.b) D11 trigger 와의 충돌**. 0.11.b 가 DGT promote 권고를 산출하면 본 phase 의 D3 후보 식별이 *이미 결정된 것*처럼 흐를 risk (DGT 가 특정 자산에 합류). Mitigation: §1.6 Independence Declaration.
- **R5 (MEDIUM) — 의미 재정의** (Round 1 ITERATE Patch 8): **composition.py:232-243 단일 strategy 인스턴스 공유 패턴 해제 시 cascading risk**. 이전 표현 "`AssetContext` 의식 → 코드 승격" 은 부정확 — `AssetContext` 는 이미 `asset_context.py:37-57` 에 구현 + `composition.py` / `DailyOrchestrator` 에서 사용 중 (증거 7 + 잠정 결론 정정). 실제 변경 surface = (a) `composition.py:232-243` 단일 strategy 인스턴스 공유 제약 해제, (b) `yaml_strategy_config_loader.py:157-201` `_check_policy_uniformity` 완화, (c) Phase 0.7.3 baseline 보존 invariant 측정 (`per_asset_strategy_overrides=None` single-strategy 동작 회귀 검증). Mitigation: §1.6 Independence Declaration + D11 트리거 + 본 phase 진단 보고서가 `AssetContext` 기존 구현 발견 명시 박제.
- **R6 (LOW)** — **회귀 invariant 박제의 자기참조**. D8 이 "Phase 0.7.3 baseline 보존" 을 박제하는데, baseline 자체가 single-strategy 가정 하의 산출 → multi-strategy 도입 시 비교 의미 자체 재정의 필요. Mitigation: D8 후속 phase 박제 대상으로 위임.
- **R7 (LOW)** — **본 ADR 의 박제 자체가 작성 금지 위반 risk**. CLAUDE.md §14 "Phase 1 진입 전 작성 금지" 목록에 "종목별 다른 정책" 이 명시되어 있음. 본 phase = *진단 + 설계 박제 only / 코드 변경 zero* 이므로 §14 위반 아님 (§13.3 "친절한 추가 금지" 정신 정합). Mitigation: §1.6 + §1.7 명시.
