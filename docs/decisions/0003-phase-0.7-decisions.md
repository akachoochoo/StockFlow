   종목 전제는 자산군 다변화도 포함하는 일반 분산 정신.
3. **KR 거래소 KRW 결제 ETF 의 KR 시장 sentiment 동조 한계** — §13.4

**후속 처리**:

- 지역 분산 검증은 **Phase 0.7.2+ 또는 데이터 가용성 개선 시점** (e.g.
  KIS API 직접 거래 또는 5 년 데이터 누적 후) 으로 미룸. ADR §10.1

- 본 §1.2.4 갱신은 "지역 분산은 영영 폐기" 가 아닌 "Phase 0.7.1 데이터
  제약 하 자산군 분산으로 우회" 박제. Phase 0.7.2+ 진입 시 본 §1.2.4
  재검토 라운드 진입.
- 본 갱신은 §13.7 (가칭 — Phase 0.7.2 진입 결정 라운드) 에서 정합성

#### 2.2.6 자본 활용률 측정 방식 박제 (라운드 #4)

ADR §2.3 의 "자본 회전율 (per-asset 평균)" 항목 정밀화:

- **per-asset budget** = `initial_capital / N` = 100,000,000 / 2 = **50,000,000 KRW**
  (Phase 0.7.1 균등 배분 ADR §4.1 정합).
- **per-asset committed_capital_t** = 시점 t 의 해당 자산 position 의
  `quantity × avg_price` (PortfolioSnapshot 의 PositionValuation 의
  cost_basis 와 동일).
- **per-asset utilization_t** = `committed_capital_t / per_asset_budget`.
- **per-asset avg_utilization** = 시간평균 (모든 trading day 평균).
- **portfolio avg utilization** = `mean over assets of per_asset_avg_utilization`
  (산술평균, 가중 안 함 — 균등 배분 정합).

**Phase 0.5 비교**: Phase 0.5 F 의 19.4 % 는 단일 자산 (069500) 50M 한정
budget 가정 (Phase 0.7.1 환경 정합). Phase 0.5 F 의 백테스트 환경은
실제로는 100M initial + 7 splits × 10M (= 70M capacity) 였으므로 19.4 %
는 단일 자산이 100M 기준 활용한 비율. 본 §2.2.6 박제 (50M per-asset
budget) 는 Phase 0.7.1 환경에서의 정량 측정 — Phase 0.5 와 같은
"per-asset 50M budget" 가정 하에 19.4 % 가 그대로 baseline 으로 유효
(per_split_amount 는 다르지만 % utilization 은 자본 단위와 무관 invariant
검증 가능).

#### 2.2.7 비교 baseline 자본 100M 정합성 박제

- 단순 (0.7.1 학습 목표는 인프라 작동 확인, 정책 비교 아님).
- 변수 통제: 0.7.1 = 종목 수만 변수. per_split_amount 유지 시 capacity 가
  initial 100M 기준 8 split 까지 가능 → 한 종목 7 split 다 채워도 다른
  종목 진입 가능 (cash 분리 가정). per_split_amount 를 5M 으로 절반화 →
  per-asset capacity 10 split → max_split_count=7 의 여유가 같음 (Phase
  0.5 와 동일한 capacity 비율 유지).

### 4.2 0.7.2 — 배분 정책 비교

3-way 비교:

| 정책 | 산출 |
|---|---|
| **균등** | per-asset budget = initial / N |
| **시총 가중** | per-asset budget ∝ market cap |
| **변동성 가중** | per-asset budget ∝ 1 / 일별 return std |

학습 목표: 분산 효과는 정책에 따라 어떻게 달라지는가?

미결 사항:
- 시총 / 변동성 측정 윈도우 (Phase 0.5 와 같이 t-1 까지, 룩어헤드 회피)
- 정적 vs 동적 (Phase 0.7.2 는 정적 — 백테스트 시작 시점 1회 측정)

### 4.3 0.7.3 — 종목 다양화 후 정책 재평가

3 ~ 5 개 조합에서 §4.2 정책 재측정 (단계 분리 ADR §10).

## 5. 종목 간 우선순위

### 5.1 결정 — 옵션 a (config 정의 순서)

**결정**: 같은 날 두 종목 모두 매수 트리거 충족 시 **config YAML
정의 순서대로** 실행.

근거:
- 단순 (사용자 박제 인용: "옵션 a (단순)").
- 결정 가능성 (deterministic): 동일 입력 → 동일 결과 보장.
- 향후 확장성: 0.7.3 에서 score-based 비교는 ADR 0003 §13+ 박제 후 진입.

### 5.2 매도 우선순위

매도는 **종목 간 우선순위 무관 — 종목별 독립 판단**:
- 각 종목의 매도 트리거는 종목 자체 position / current_price 기반
- 종목 간 자본 이동 없음 (§6) → 한 종목의 매도가 다른 종목의 매수에 영향
  없음 (cash budget 독립)

### 5.3 cash 부족 시 (idempotency 충돌 보강)

같은 날 종목 A 매수 후 cash 부족 → 종목 B 매수 skip:
- skip reason: `INSUFFICIENT_BALANCE` (기존 SkipReason 그대로 활용)
- Decision 의 reasoning 에 `priority_order: [A, B]`, `skipped_due_to_insufficient_balance: B` 박제
- per-asset budget 분리 가정 (§4.1) 하에서는 거의 발생 안 하지만 방어
  코드는 유지

## 6. 종목 간 자본 이동

### 6.1 결정 — 없음 (옵션 a)

**결정**: Phase 0.7 동안 종목 간 자본 동적 이동 없음. per-asset budget
고정.

근거 (사용자 박제 인용):
> 옵션 a: 종목별 capital_allocation 고정 (이동 없음). Phase 0.7 단순화.

### 6.2 idle cash 처리

종목 A 의 7 split 모두 발화 + 회복 매도 → A 의 cash 가 idle.
- A 의 cash 는 **A 의 next 진입 까지 idle 유지**
- B 에게 흘려보내지 않음 (정적 budget)

→ Phase 0.5 §12.4.4 (cash idle 활용) 의 "멀티 자산 분산" 접근은 §3.3
종목 추가로 부분 해결 (각 종목이 idle 시간이 다르게 분포). 동적 이동은
**Phase 1+ 별도 ADR 결정**.

### 6.3 미결 — Phase 1+ 검토 항목

| 항목 | 시점 |
|---|---|
| 동적 자본 이동 정책 (한 종목 idle → 다른 종목 추가 발화) | Phase 1+ ADR (KIS 실거래 환경에서 운영 데이터 확보 후) |
| 채권 / 단기 예치 활용 (idle cash 의 무위험 수익) | Phase 1+ |

## 8. 멀티 종목 인프라 (Orchestrator 확장)

### 8.0 현재 상태 점검 (CLAUDE.md §16 의식 준수도)

CLAUDE.md §16.1 / ADR 0002 §7.1 의 "단일 asset 시그니처 + 내부 loop-ready"
권고 패턴 점검 결과:

| 항목 | 상태 |
|---|---|
| `DailyOrchestrator.__init__` 단수 (`asset: Asset`) | ✅ |
| `run_for_date(today)` 단수 시그니처 → `Decision` 단수 반환 | ⚠️ 멀티 시 변경 필요 |

| Position / Repository asset_fqn 키 기반 독립 | ✅ |

→ §16 권고 패턴은 부분 충족. Phase 0.7.1 에서 본격 리팩토링 진입.

### 8.1 리팩토링 결정 — DailyOrchestrator 확장 (새 클래스 신설 안 함)

**결정**: 기존 `DailyOrchestrator` 를 list[Asset] 처리하도록 확장. 새
`MultiAssetOrchestrator` 클래스 신설 안 함.

근거:
- Phase 0.7 의 단일 → 2종목 최소 변경 원칙. 새 클래스 신설은 큰 surface
  area 증가.
- Phase 0/0.5 의 모든 테스트가 `DailyOrchestrator` 직접 인스턴스화 →
  새 클래스 도입은 마이그레이션 비용 큼. 기존 클래스 시그니처 변경이
  CLAUDE.md §13.3 "친절한 추가 금지" 정신과 정합.

### 8.2 시그니처 변경 박제 (Phase 0.7.1 박제 사항)

```python
# 현재 (Phase 0.5)
class DailyOrchestrator:
    def __init__(
        self, *, broker, market_data, signal,
        strategy: PriceDropStrategy,
        config: SplitStrategyConfig,
        sell_strategy: SellStrategyPort,
        sell_config: SellStrategyConfig,
        asset: Asset,
        clock, uow_factory,
    ): ...
    def run_for_date(self, today: date) -> Decision: ...

# Phase 0.7.1 후
class DailyOrchestrator:
    def __init__(
        self, *, broker, market_data, signal,
        asset_contexts: list[AssetContext],  # 신규 — 종목별 컨텍스트 묶음
        clock, uow_factory,
    ): ...
    def run_for_date(self, today: date) -> list[Decision]: ...

@dataclass(frozen=True)
class AssetContext:
    asset: Asset
    strategy: PriceDropStrategy
    config: SplitStrategyConfig
    sell_strategy: SellStrategyPort
    sell_config: SellStrategyConfig
```

**근거**:
- AssetContext 묶음 → §5.1 우선순위 = `asset_contexts` 리스트 순서 그대로.
- 단수 → list 시그니처 변경은 **호출자 (BacktestRunner / PaperRunner / CLI)
  도 동시에 변경**. ADR 0002 §11 sub-step 분할 정신상 한 commit 에 묶임.

### 8.3 내부 helper 메서드 변경

`_compute_outcome(today)` 가 `self._asset` 직접 사용 → 다음 패턴으로:

```python
def run_for_date(self, today: date) -> list[Decision]:
    decisions = []
    for ctx in self._asset_contexts:  # §5.1 순서대로
        outcome = self._compute_outcome_for_asset(ctx, today)
        self._persist(outcome)  # 자산별 단일 UoW (§8.4)
        decisions.append(outcome.decision)
    return decisions

def _compute_outcome_for_asset(
    self, ctx: AssetContext, today: date,
) -> _Outcome: ...
```

`_run_sell_loop`, `_handle_no_buy`, `_buy_idempotency_key`,
`_sell_idempotency_key`, `_base_reasoning` 등 helpers 모두 `ctx` 파라미터
받도록 변경.

### 8.4 Persistence — 자산별 단일 UoW

**결정**: 자산별 1 회 UoW commit. 멀티 자산 단일 UoW 묶지 않음.

근거:
- ADR 0001 §8.5 의 단일 UoW 정신은 "한 자산 결정의 atomic persistence".
- 멀티 자산을 1 UoW 로 묶으면 한 자산 실패 시 다른 자산 결정 손실 → 단일
  자산 환경에서 실패 격리 깨짐. 자산 간 독립성 (§5.2 매도 독립) 정신과
  정합.
- 자산 A 의 commit 실패가 자산 B 의 commit 에 영향 없음 (독립).
- 한 자산 IntegrityError 는 즉시 전파 → 후속 자산 처리 중단 (CLAUDE.md
  §6.1 정신).

### 8.5 idempotency key 자산 unique 검증

ADR 0002 §5.9.1 / §12.4.5 박제: 현 키 형식 `{asset.fqn}:{date}:{side}:{slot}`
은 자산 간 unique 보장.

검증 사항 (Phase 0.7.1 회귀 테스트):
- `tests/integration/test_multi_asset_idempotency.py` 신규 — 같은 날
  종목 A / B 동시 매수 시 key 충돌 없음 + DB unique 제약 위반 없음
- 종목 A 의 BUY 와 종목 B 의 SELL 같은 슬롯 번호 사용해도 unique

### 8.6 reconciliation (CLAUDE.md §11.2) 자산별

매일 시작 시 종목별 DB position vs 브로커 position 대조:
- Phase 0.7.1 박제: **종목별 독립 reconcile**
- 한 종목 mismatch 발견 → 해당 자산만 정지 vs 전체 정지?
- **결정**: 0.7.1 은 **전체 정지** (단순). 자산별 정지 분기는 Phase 1
  ADR 결정 항목.

**임계치 0.5 근거**:

§13.2 fallback 트리거인 Pearson r ≥ 0.5 의 박제 근거:

1. **분산 효과 정량 의미** — Pearson r = 0.5 → 결정계수 R² = 0.25. 한
   자산이 다른 자산의 분산을 25 % 설명. 75 % 는 독립적 변동 → 분산
   투자 이론상 "moderate diversification" 임계.
2. **검증력 정합성** — ADR §1.2 진입 근거 ("H2/H3 미충족의 본질이 단일
   종목의 사이클 의존") 직접 검증. r ≥ 0.5 면 두 종목이 사실상 같은
   사이클 → 단일 종목 가설 검증 불가.
3. **균형** — 너무 낮은 임계 (e.g. 0.2) 는 KR 거래소 ETF 한정으로 달성
   어려움. 너무 높은 임계 (e.g. 0.7) 는 사실상 분산 효과 없는 종목도
   통과 → §1.2 검증 정신 약화.
4. **재현성** — 0.5 는 Pearson 의 standard moderate-correlation 경계로
   학계/실무 양쪽 사용 — 임의값 아님. 후속 phase 에서 임계치 변경 시
   data snooping 위험 차단 가능 (Phase 0.5 §6.5 정신 인용).

본 임계치는 Phase 0.7 동안 고정. 변경 시 ADR §13+ 또는 후속 ADR 박제
+ data snooping 회피 명분 박제 필수.

### 14.5 결과 해석

**1. H3 (Sharpe) 임계 근접 미달**:

Phase 0.7.1 multi Sharpe 0.3258 = Phase 0.5 F (0.2977) 대비 +0.0281 개선.
임계 0.39 와 0.0642 차이. 자산군 분산이 위험관리에 substantial 기여
(§14.5.2 MDD 개선 참조) — 그러나 return 하락이 Sharpe 상승을 제한함.

**2. MDD 대폭 개선 — 자산군 분산의 위험관리 가치 확인**:

Phase 0.5 F -15.9017 % → Phase 0.7.1 multi -7.9487 % (+7.9530pp 개선).
ADR §1.2.4 갱신 정신 ("자산군 분산은 위험관리 가치") 데이터 검증.

**3. H1 (자본 활용) 본질적 미달 — 채권 dormant 특성**:

채권 ETF (214980) low volatility → PriceDropStrategy 5 % drop trigger 거의
미발화 → ProfitTargetSell +10 % 도 미발화 → 자본 idle. 채권 자산군에
주식 전략 그대로 적용 불일치.

**4. H2 (return) — 자본 희석 + 회복기 기회비용**:

Phase 0.5 F +9.42 % → Phase 0.7.1 multi +5.25 % (-4.17pp). 채권 자산이
자본 50 % 점유했으나 거의 거래 안 함 → 주식 자산 (069500) 회복 수익이
자본 절반 만 흡수 → portfolio return 희석.

| 정책 | 산식 | 의도 |
|---|---|---|
| **균등 (baseline)** | `budget_i = total / N` | Phase 0.7.1 그대로. 비교 baseline |

#### 16.13.5 산식 박제

```
σ 산출 (모든 정책 공통, 필요 시 호출):
  daily_log_returns_i = log(close_t / close_{t-1}) for t in lookback (246)
  σ_i = stddev(daily_log_returns_i) × √246  (annualized — but 비교 정합용
                                              raw stddev 도 가능, 결정
                                              사항)

EQUAL (default):
  per_split_amount_i = yaml.per_split_amount_i  (그대로)

INV_VOL:
  weight_i = (1 / σ_i) / Σ_j (1 / σ_j)
  per_asset_budget_i = total × weight_i
  per_split_amount_i = per_asset_budget_i // max_split_count_i

VOL:
  weight_i = σ_i / Σ_j σ_j
  per_asset_budget_i = total × weight_i
  per_split_amount_i = per_asset_budget_i // max_split_count_i
```

부속 결정 — annualization (× √246) 적용 여부:

  채택. 두 자산 간 상대 비중 산정 시 √246 은 양쪽에 동일 곱해지므로
  weight 산출 결과 무차별 (수학적 동치). 단순화 + 테스트 검증 단순.
