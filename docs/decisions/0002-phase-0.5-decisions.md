## 1. Phase 0.5 목적

### 1.0 배경

Phase 0 회고(`docs/retrospectives/phase-0.md` §3.4)에서 5년 KOSPI 200
백테스트 결과 핵심 한계로 부각:

> 7회 분할 모두 COVID 1차 충격(2020-01~03 76일) 안에 발화 → 이후 4.7년
> dormancy. 매도 로직 부재가 가장 큰 기회비용.

전략의 +4.82pp 초과수익(B&H 대비)이 진정한 알파인지, 아니면 단지 COVID
저점 매수의 우연인지 판별할 유일한 방법은 **매도 로직 추가 후 재백테스트**.
회복기에 익절하고 회수된 자본이 다음 변동성에 재투입되는 흐름이 작동
하는지가 핵심 검증 지점.

### 1.1 Phase 분할 결정

| Phase | 범위 | 목적 |
|---|---|---|
| **Phase 0.5** | 매도 로직 + 재진입 (단일 종목) | 매도 효과 단독 검증 |
| Phase 0.7 | 멀티 종목 + 자본 배분 | 종목 다변화 효과 단독 검증 |
| Phase 1 | KIS API + 모의투자 + 매도 텔레그램 | 실거래 진입 |

**분할 이유:** 변수 분리 측정. 매도와 멀티 종목을 한 phase에 묶으면
"어느 변경이 결과를 만들었나" 판별 불가능. 한 번에 한 변수 (CLAUDE.md
§13.1 "추측하지 말 것" 정신).

### 1.2 Phase 0.5 완료 조건 (선언적)

§10에서 운영 기준으로 상세화. 본 §1.2는 비전:
- 매도가 작동한다 (분할별 독립 +10% 익절)
- 재진입이 작동한다 (D, F 두 정책 양쪽)
- 백테스트 ↔ 페이퍼 동일성 invariant 여전히 유지
- D vs F 5년 비교 결과 박제 + Phase 0.5 회고 작성

### 1.3 가설 (Hypothesis)

**핵심 가설:** Phase 0의 +4.82pp 초과수익 중 일부는 우연(COVID 저점 매수의
타이밍 효과)이고, 매도 + 재진입 도입 시:

- **H1 (자본 회전 알파)**: 회수된 자본이 후속 변동성에 재투입되면서 Phase 0 baseline 대비 **자본 회전율이 N배 이상 증가**한다 (N ≥ 2 가정).
- **H2 (총 수익 우월)**: 정책 D 또는 F 중 적어도 하나가 Phase 0 baseline의 +25.96 % 총 수익을 능가한다.
- **H3 (위험조정 수익 유지/개선)**: Sharpe ratio가 Phase 0의 0.39 대비 ≥ 0.39 (위험조정 수익 악화 없음).
- **H4 (D vs F 차별화)**: D와 F의 결과가 measurably 다르다 (단순 노이즈 수준 이상). 차이가 미미하다면 추가 정책 다양성은 Phase 0.7+로 미룬다.

### 1.4 반증 기준 (Falsifiability)

각 가설이 **거짓**으로 드러나는 경계:

| 가설 | 거짓 판정 조건 | Phase 0.5 액션 |
|---|---|---|
| H1 | 자본 회전율이 Phase 0 대비 2배 미만 | 매도 임계치 또는 재진입 정책 가정 재검토 |
| H2 | D, F 둘 다 Phase 0 baseline 미달 | 매도 임계치(+10%) 자체 재검토 (회고 ADR §12 신규) |
| H3 | Sharpe < 0.30 (악화) | 매도가 변동성을 가산했음 — 손절 도입 우선순위 상승 |
| H4 | D, F 결과 차이 ≤ 1pp (return) AND ≤ 5% (회전율) | Phase 0.5 단일 정책 채택 + 추가 정책 Phase 1+ |

H1·H2·H3 모두 거짓이면 Phase 0.5의 결론은 "매도 도입 무용 또는 해롭다"
가 되며, Phase 0.5 회고 §7에서 Phase 1 KIS API 직진 권고 (매도 보류).

### 1.5 Phase 0.7 진입 기준

다음 게이트 모두 통과 시 Phase 0.7 진입 가능:

1. ✅ Phase 0.5 §10 완료 게이트 4건 모두 통과 (코드 품질, invariant, 실데이터, 회고)
2. ✅ H1·H2·H3 중 ≥ 2 가설이 참 (즉, 매도가 가치 추가)
3. ✅ Phase 0.5 회고에서 사용자 + AI가 **D 또는 F 중 하나를 default로 채택** 결정 박제
4. ✅ 멀티 종목 도입 시 우려 사항 (자본 배분, 동시 매수 시 idempotency 충돌, 종목 우선순위) 식별 + Phase 0.7 ADR 라운드 트리거

## 2. 매도 정책

### 2.1 분할별 독립 매도 (박영옥 원전)

- **결정**: 7개 분할 슬롯 각각이 독립적으로 매도 평가. 한 슬롯이 매도
  조건 충족하면 해당 슬롯만 매도, 다른 슬롯은 영향 없음.
- **이유**: 박영옥 "주식투자 절대지식"의 7분할 매매 원전이 분할별 독립
  관리. 평단가 기준 매도(전체 포지션 일괄)와 다른 패러다임 — 분할별
  독립이 자본 회전과 추적 가능성에서 우위.
- **트레이드오프**: 부분 매도라 수수료 누적 증가. Phase 0 Mock에서는
  수수료 0이라 무관. Phase 1 KIS API 도입 시 수수료 모델 추가.

### 2.2 매도 임계치 (단순 +10 %)

- **결정**: 각 슬롯 `entry_price` 대비 `current_price` 가 +`profit_target_pct` (기본 10.0) 이상이면 매도 트리거.
- **모든 슬롯 동일 임계치** — 슬롯별 차등 임계치는 Phase 0.5 제외 (Phase 0.7 회고 후 재검토).
- **이유**: Phase 0.5는 "매도가 작동하는가" 검증이 목표. 임계치 튜닝은
  변수가 늘어나 검증 노이즈. 박영옥 원전도 단순 % 기준.
- **트레이드오프**: 횡보장에서 +10% 도달 못 하면 매도 안 됨 → 매수만
  하는 Phase 0와 동일 거동. 의도된 단순성.

### 2.3 동시 트리거 처리

- **결정**: 한 evaluation에서 N개 슬롯이 동시 매도 트리거되면 **모두
  매도**. 우선순위 없음.
- **이유**: 우선순위 정책 도입은 또 하나의 변수. 단순성 우선.

### 2.4 부분 매도 불가

- **결정**: 한 슬롯은 통째로 매도하거나 안 함. 슬롯 안 50 % 매도 등의
  세분화 없음.
- **이유**: 슬롯이 이미 분할 단위. 추가 분할은 복잡성 폭증.
- **재검토**: Phase 1+에서 RuleBasedSignal이 부분 매도 신호를 보낼
  경우 재고.

### 2.5 손절 미도입 (Phase 0.5)

- **결정**: 평단 기준 -X % 손절 정책 **Phase 0.5에서 도입 안 함**.
- **이유**: Phase 0.5는 익절 + 재진입의 알파만 측정하는 게 목적. 손절
  추가는 또 하나의 변수. 박영옥 원전도 손절 강제 안 함 (오히려 분할
  매수 강도 증가로 평단 낮춤).
- **CLAUDE.md §11.4 정책**: "추가 매수 자동 정지 + 사람 개입 대기"는
  유지 (max_loss_pct 도달 시).
- **재검토**: Phase 1 실거래 진입 시 — Mock 백테스트와 실거래의
  최대 차이는 최악 시나리오 보호. 손절은 그 때 필수 검토.

## 3. 슬롯 모델 도입

### 3.1 SplitSlot 값 객체

- **결정**: 새 ValueObject `SplitSlot` 도입. 7개 고정 슬롯이 매도/재진입
  사이클을 거치며 EMPTY ↔ FILLED 전환.

  ```python
  class SplitSlot(ValueObject):
      slot_number: int = Field(ge=1, le=7)        # 고정, 1..7
      state: SlotState                              # EMPTY | FILLED
      entry: SplitEntry | None                      # FILLED일 때만 not None
      last_exit_price: Decimal | None               # 직전 매도가 (재진입 정책 F용)
      last_exit_date: date | None                   # 직전 매도일 (cooldown 계산용)
  ```

  Invariants (`@model_validator`):
  - `state == FILLED ⇔ entry is not None`
  - `state == EMPTY ⇒ entry is None` (그러나 last_exit_* 는 가능 — 재진입 대기 슬롯)
  - `last_exit_date is not None ⇒ last_exit_price is not None`

- **`SlotState` enum**: `EMPTY` / `FILLED`.

### 3.2 Position 마이그레이션 (entries → slots)

- **결정**: `Position.entries: list[SplitEntry]` 제거. `Position.slots: list[SplitSlot]` 신규.
- **`split_level` 의미 변경**: "채워진 슬롯 개수" = `sum(1 for s in slots if s.state == FILLED)`. 매도 시 감소 가능.
- **신규 invariants**:
  - `len(slots) == max_split_count` (Phase 0.5: 7로 고정)
  - `slot_number` 1..N 연속, 정렬 보장
  - `quantity == sum(s.entry.quantity for s in slots if s.state == FILLED)`
  - `avg_price == weighted_avg(s.entry.entry_price * s.entry.quantity for FILLED slots)` (정확 일치, Phase 0의 5개 invariant 중 1개 그대로)
  - `quantity == 0 ⇒ split_level == 0` 그러나 last_exit_* 는 보존 가능
- **마이그레이션 영향 범위 (사전 식별)**:
  - `src/domain/models.py::Position` 본체
  - `src/domain/strategies/price_drop.py` (entries 참조)
  - `src/use_cases/daily_orchestrator.py`
  - `src/adapters/mock/broker.py::_update_position` (entries 추가/갱신 로직)
  - `src/infrastructure/repositories/sqlite_position_repo.py` (저장 schema)
  - `src/application/snapshot_builder.py` / `backtest_runner.py` (참조 가능성)
  - 모든 관련 단위 + 통합 테스트

### 3.2.1 부분 체결 차단 정책 (Phase 0.5 한정)

- **결정**: Phase 0.5에서 **부분 체결을 BUY/SELL 양쪽에 대해 차단**.
  - `MockBroker.__init__`: `simulate_partial_fill_rate=0.0` 강제 (생성자에서 0이 아닌 값을 받으면 raise).
  - `BacktestRunner` / paper composition root에서 MockBroker 생성 시 옵션 노출 안 함.
- **이유 (강화)**:
  - §3.2 invariant 강화 (`quantity == sum(...)` 등호화)와 일관 — partial fill carry 의 도메인 모델이 사라졌으므로 broker도 발생시킬 수 없게 차단.
  - 부분 매도 모델 부재(§5.6)와도 대칭. BUY만 partial 허용하면 슬롯 무결성 깨짐.
  - Phase 0.5의 검증 목표는 "매도/재진입 정책 알파 측정". partial fill 노이즈는 측정을 흐림.
- **Phase 1 KIS 본격화**:
  - 실 KIS API는 partial fill을 자연스럽게 발생시킴.
  - Phase 1 진입 직전 별도 ADR 라운드에서:
    - 부분 체결 도메인 모델 부활 (혹은 새 설계)
    - 슬롯 invariant 완화 (`quantity == sum + pending_carry`)
    - 부분 매도 정책 (재시도 vs 큰 슬롯 분할 vs reject)
- **재검토**: Phase 1 ADR §1 (KIS API 도입 시).

### 3.3 sparse split_number 허용

- **결정**: 매도/재진입 반복 시 `slot_number=2`가 EMPTY인 채 `slot_number=3`이 FILLED인 상태 정상.
- **이유**: 박영옥 원전의 "각 슬롯이 자기 사이클을 가짐" 패러다임 박제.
- **`SplitEntry.split_number`**: Phase 0의 `1, 2, …, split_level` 연속 invariant **제거**. 이제 슬롯 식별자.

### 3.4 데이터 마이그레이션 정책

- **결정**: Phase 0 SQLite 스키마와 호환되지 않음. **빈 DB로 시작**.
- **이유**: Phase 0 데이터는 검증용 fixture지 운영 자산 아님 (회고 §1).
  실거래 데이터 마이그레이션은 Phase 1 진입 직전 별도 ADR 라운드.
- **박제할 것**: 본 §3.4와 함께 "Phase 0 → Phase 1 운영 전환 시
  마이그레이션 스크립트는 별도 ADR 라운드"라는 정책. 자동 마이그레이션
  코드는 Phase 0.5에서 작성 안 함.

## 4. 재진입 가격 정책

### 4.1 ReentryPriceStrategy Protocol + Anchor 선택 framework

- **결정**: 재진입 트리거 가격 계산을 Strategy 패턴으로 분리. Phase
  0.5는 두 정책 (`MovingAverageReentry`, `HybridTimeBasedReentry`)을
  비교한다.

  ```python
  class ReentryPriceStrategyPort(Protocol):
      def get_trigger_price(
          self,
          *,
          slot: SplitSlot,
          position: Position,
          current_price: Decimal,
          drop_threshold_pct: Decimal,
          as_of: date,
      ) -> Decimal | None:
          """빈 슬롯 재진입 트리거 가격을 반환.

          ``None`` = 데이터 부족(예: SMA window 미충족) → 호출자는 이 슬롯을
          평가에서 제외한다. ``Decimal`` 값일 때 호출자는 ``current_price <=
          trigger_price`` 를 비교해 매수 여부를 결정.
          """
          ...
  ```

- **반환 타입 `Decimal | None`**: §4.10 데이터 부족 fallback과
  연결 — strategy가 명시적으로 "이 슬롯은 트리거 계산 불가" 신호를
  보낼 수 있어야 함.

#### 4.1.1 Anchor 선택 framework (사용자 검토 4차 박제)

새 재진입 정책 추가 시 평가표 — Phase 1+에서 ML/momentum/volatility-band
정책 도입 시에도 동일 framework 재사용.

| 후보 anchor | 트리거 의미 | 자기참조? | Phase 0 호환 | 자본회전 | 채택 |
|---|---|---|---|---|---|
| `current_price` (today close) | self-referential | ❌ `current ≤ current × 0.95` 항상 false | - | 0 | **폐기 (D)** |
| `position.avg_price` | Phase 0 기존 동작 | ✓ | 매우 높음 | 중 | 보류 (Phase 1+ 후보) |
| **moving average (window N)** | **시장 추세 기반** | ✓ | 새 차원 | 적극적 | **채택 (D-2)** |
| `slot.last_exit_price` (cooldown) | 슬롯 역사 기반 | ✓ | 새 차원 | 보수적 | **채택 (F)** |
| EMA / MACD / RSI 등 | 보조지표 기반 | ✓ | 새 차원 | varies | Phase 1+ |

**D 폐기 근거 박제**: 초기 ADR §4.2의 "현재 시장가 기준" 정책 D
(`trigger = current_price × (1 - drop_pct/100)`)는 자기참조라 매수 발화가
불가능하다. 0.5.10 구현 직전 발견되어 폐기되고 D-2 (MovingAverageReentry)
로 대체.

### 4.2 정책 D-2 — `MovingAverageReentry`

- **YAML name**: `"moving_average"`
- **파라미터**:
  - `window: int` (기본 20) — N 영업일 이동평균
  - `ma_type: str` (기본 `"sma"`) — Phase 0.5는 SMA만, EMA는 Phase 1+에서 sub-type 확장
- **공식**:
  - 첫 매수 (`slot.last_exit_date is None` AND `position.split_level == 0`) → `return current_price` (§4.7 first-buy bypass)
  - 그 외:
    - 데이터 fetch (§4.10 정책 적용)
    - bars 길이 < window → `return None` (§4.10 fallback)
    - `sma = mean(bar.close for bar in bars[-window:])`
    - `return sma × (1 - drop_threshold_pct / 100)`
- **의존성 주입**: `__init__(market_data: MarketDataPort, window: int = 20, ma_type: str = "sma")`.
- **장점**: 시장 추세 기반 anchor → 우상향에서도 SMA 따라 자연스럽게 buy
  zone 상승. 자본 회전 적극적.
- **단점**: 데이터 부족 (시스템 시작 직후 N일 미만) 동안 재진입 불가능.
  단, 첫 매수만은 §4.7 bypass로 발화.

### 4.3 정책 F — `HybridTimeBasedReentry`

- **YAML name**: `"hybrid"`
- **파라미터**: `cooldown_days: int` (기본 60).
- **의존성 주입**: `__init__(cooldown_days: int = 60)` (외부 데이터 의존 없음).
- **공식**:
  - `position.split_level == 0` (=position is None OR 모든 슬롯 EMPTY 이력
    없음) → §4.7 first-buy bypass: `return current_price`.
  - 슬롯에 `last_exit_date` 있음 → cooldown 룰 (§4.6, 0일 포함):
    `return slot.last_exit_price × (1 - drop_threshold_pct / 100)`
    cooldown 경과 후에도 동일 (Phase 0.5는 last_exit anchor 유지 — 단순성,
    두 정책의 직교 비교; Phase 1+에서 D-2 위임 옵션 검토).
  - **fresh slot in non-empty position** (slot.last_exit_date is None
    이지만 position.split_level >= 1):
    `return position.avg_price × (1 - drop_threshold_pct / 100)`
    Phase 0 D 행동 (avg_price drop check) 호환. 사용자 검토 5차 박제.
- **반환 타입**: 항상 `Decimal` (None 케이스 없음 — 외부 데이터 미의존).

### 4.4 매수 전략과의 결합

- **결정**: `PriceDropStrategy` 가 `ReentryPriceStrategyPort` 를 **필수**
  의존성으로 주입받음. 디폴트 정책 없음 — composition root에서 명시.
  사용자 검토 (a) 참조: default가 어떤 정책으로 편향되면 비교 가치 손상.
- **시그니처 변경**:
  ```python
  PriceDropStrategy(reentry: ReentryPriceStrategyPort)
  ```
- **첫 매수**: §4.7 bypass — 정책에 위임하되 정책이 `current_price` 자체를
  반환해 자동 발화시킴 (어떤 정책이든 동일 거동).
- **슬롯 선정**: §4.8 algorithm. 트리거 충족 슬롯들 중 가장 작은
  `slot_number` 우선.

### 4.5 정책 비교 가치 — "추세 vs 슬롯 역사"

D-2 vs F는 **다른 차원**의 정책 — 단순 보수성/적극성 비교가 아니다:

- **D-2 (MovingAverageReentry)**: anchor가 **시장 추세** (외부 신호). 슬롯
  역사 무시. 우상향이면 buy zone도 상승 → 적극적. 횡보·하락이면 buy zone도
  움직임 → 가격 따라간다.
- **F (HybridTimeBasedReentry)**: anchor가 **슬롯 자체 역사** (내부 상태).
  매도 직후 보수, 시간 흐르면 (Phase 1+ 위임 옵션 도입 시) 추세 기반.

따라서 §8 백테스트에서 두 정책은 **상이한 시장 국면에서 상이한 강점**을
보일 가능성이 높다. 단일 우열 판정 금지 — 시장 상황별 분석 필수.

§8 측정 지표 (자본 회전율, 누적 매도 횟수, 평균 자본 활용률) 그대로
사용.

### 4.6 Cooldown 경계 0일 케이스 (사용자 검토 3차 박제)

- **결정**: 정책 F 에서 `days_since_exit == 0` (매도 당일)도 cooldown 모드.
  즉 `last_exit_price` 기준 보수적 트리거.
- **공식 정밀화**: cooldown 안 = `(as_of - last_exit_date).days < cooldown_days`.
  같은 날 매도 → 같은 날 재진입 시도해도 `last_exit_price` 사용. 자기 자신을
  팔자마자 사는 시나리오에서도 일관된 보수적 거동.
- **이유**: 박영옥 원전의 "방금 매도한 슬롯은 보수적 재진입" 정신.
- **테스트**: `test_hybrid_reentry_on_exit_day` (0일 경계).

### 4.7 첫 매수 정책 (사용자 검토 3차 박제, 5차 갱신)

- **결정 (좁힌 정의)**: **`position is None` OR `position.split_level == 0` 일 때만**
  ReentryPriceStrategy를 우회하고 현재 시장가로 가장 작은 EMPTY slot에
  즉시 진입.
- **5차 갱신 근거**: 초기 §4.7은 "last_exit_date is None 인 모든 빈 슬롯"
  으로 일반화했으나, 그러면 slot 1 FILLED + slot 2 fresh (이력 없음) →
  bypass → 즉시 매수가 되어 7일 안에 모든 슬롯이 가격 무관하게 채워짐
  (Seven Splits 분할 매수 의도와 정면 충돌). 5차 검토에서 발견 → 좁힘.
- **subsequent split의 fresh slot 처리**: 정책에 위임. 정책별 fallback:
  - **정책 F**: `position.avg_price × (1 - drop_pct/100)` (Phase 0 D 행동
    호환, §4.3).
  - **정책 D-2**: SMA 기반 anchor (slot 이력 무관, §4.2). 자연 처리.
- **`get_trigger_price` 운영**:
  - position.split_level == 0 + slot 이력 없음 → `current_price` 반환
    (auto-fire on slot 1).
  - position.split_level >= 1 + slot 이력 없음 → 정책의 fallback 적용
    (F는 avg_price, D-2는 MA).
  - position.split_level >= 1 + slot 이력 있음 → 정책의 메인 공식 적용.

### 4.8 슬롯 선정 룰 (사용자 검토 3차 박제)

매수 평가 시 EMPTY 슬롯이 여러 개일 때 어느 슬롯을 채울지:

- **알고리즘**:
  1. 모든 EMPTY 슬롯에 대해 `trigger_price = ReentryPriceStrategy.get_trigger_price(slot, ...)` 계산.
  2. `current_price <= trigger_price` 충족 슬롯 집합 추출 (즉, 해당 슬롯이 매수 발화 조건 충족).
  3. 그 중 가장 작은 `slot_number` 선택 (deterministic).
  4. 충족 슬롯이 없으면 매수 안 함 (`should_buy=False`).
- **이유**: 박영옥 원전의 "낮은 차수부터 채운다" 일관 + 데이터 결정성. 동시
  여러 슬롯이 트리거되어도 한 번에 하나만 매수 (max_split_per_day=1 정책과
  일치, ADR 0001 §7.11).
- **테스트**: `test_slot_priority_with_partial_triggers` (5개 EMPTY 중 트리거
  3개 → slot_number 가장 작은 슬롯 선택).

### 4.9 Factory 위치 결정 (사용자 검토 3차 박제, 4차 갱신)

- **결정**: `src/domain/strategies/reentry.py` 안에
  `create_reentry_strategy(name: str, *, market_data: MarketDataPort | None = None, **params) -> ReentryPriceStrategyPort` 팩토리 함수 동거.
- **시그니처**:
  - `name="moving_average"` + `window=N` (+ `ma_type="sma"`) → `MovingAverageReentry(market_data=market_data, window=N)`
    - `market_data` 필수 (없으면 `ValueError`)
  - `name="hybrid"` + `cooldown_days=N` → `HybridTimeBasedReentry(cooldown_days=N)`
  - 알 수 없는 name → `ValueError`
- **이유**: 정책 클래스와 같은 파일 → 새 정책 추가 시 한 파일 수정으로 끝.
  YAML loader가 호출하는 단일 진입점.
- **재검토**: Phase 1+에서 정책이 늘어나면 별도 모듈로 분리.

### 4.10 데이터 fetch 정책 (사용자 검토 4차 박제)

`MovingAverageReentry`가 `MarketDataPort.get_ohlcv` 를 호출하여 N일치
historical close를 가져올 때의 정책 — 외부 데이터 의존 부분.

- **캘린더 버퍼 공식**: `buffer_days = max(int(window * 1.6) + 10, 30)`
  - window=20 → 42 calendar days (≈ 28 영업일 → 충분)
  - window=60 → 106 calendar days
  - window=200 → 330 calendar days
  - 향후 window 변경 시에도 자동 조정. 마진 `1.6` 은 KRX 영업일 비율
    (5/7 ≈ 0.71) 의 역수 + 휴장일 안전 마진.

- **Look-ahead bias 방지**:
  - `get_ohlcv(asset, start=as_of - buffer_days, end=as_of)` — `end` 는
    **exclusive** (당일 close 미사용 — `as_of` 자체의 bar 제외).
  - 이는 ADR 0001 §9.3 의 "decision-time = T-1 close visible" 정신 그대로.
    `current_price` (T-1 close) 는 strategy에 이미 주입되어 있으므로
    MA window가 그것을 포함해도 무관 (single source of truth).
  - 핵심: **as_of 의 close (T close)는 절대 MA 계산에 포함되지 않아야 함**.

- **데이터 부족 fallback**:
  - bars 길이 < window → `MovingAverageReentry.get_trigger_price` returns `None`
  - 호출자 (PriceDropStrategy) 는 `None` 반환 슬롯을 평가에서 제외
  - 모든 EMPTY 슬롯이 `None` 반환 → `BuyEvaluationResult.skip_reason = SkipReason.INSUFFICIENT_HISTORICAL_DATA` (§5.6 신규)
  - 첫 매수 (§4.7) 는 buffer 미사용 — `current_price` 즉시 반환

- **영업일 처리**: OHLCV 데이터 자체가 영업일만 포함 (market_data adapter 책임).
  "N일 이동평균" = "N 영업일 이동평균" 자연 처리. 휴장 자동 제외.

- **캐싱**: Phase 0.5 미도입. 같은 asset의 SMA를 매 evaluation마다 재계산.
  단일 자산 + 일 1회 cron이라 부담 없음. Phase 1+ 멀티 자산 + intraday
  도입 시 LRU 캐시 검토.

### 4.12 split_level vs slot_number 의미 명확화 (사용자 검토 5차 박제)

Phase 0.5 슬롯 모델에서 두 정수 식별자가 등장 — 혼동 방지 위해 명시.

| 개념 | 정의 | 변동 패턴 | 용도 |
|---|---|---|---|
| `split_level` | 현재 FILLED 슬롯의 **개수** | 매수 시 +1, 매도 시 -1, 0..max_split_count 범위 | 누적 매수 진행도 표시, max_split_count cap 비교 |
| `slot_number` | 각 슬롯의 **고정 위치 식별자** (1..max_split_count) | **불변** — 슬롯의 평생 ID | 매도/재진입 추적, sparse 패턴(예: slot 2 EMPTY + slot 3 FILLED) 표현 |

- `Position.slots` 의 길이는 항상 `max_split_count`. 각 `slot_number` 가
  1..N 중 unique 값 (ADR 0001 §3.2 invariant).
- `position.split_level` ≡ `len([s for s in slots if s.state is FILLED])`.
  Phase 0의 "split_level == len(entries)" 와 직접 호환되지만 매도 후
  감소가 가능하다는 점이 다르다.

#### Phase 0 누진 트리거 룰 정정

Phase 0 ADR 0001 §7 의 "n번째 분할 매수는 (n-1)번째 entry 대비 X% 하락 시"
룰은 sequential split_number 가정. Phase 0.5 슬롯 모델에서는:

- **트리거 비교 대상은 `slot_number` 가 아니라 `slot.entry_price` 또는
  policy fallback의 anchor**. (n번째 분할이라는 개념은 slot의 위치가 아니라
  policy의 anchor 선택과 관련.)
- 구체적으로:
  - **F 정책**: 매도 후 재진입은 `slot.last_exit_price` (그 슬롯이 직전에
    매도된 가격) 기준. fresh slot은 `position.avg_price` 기준 (Phase 0 호환).
  - **D-2 정책**: 모든 EMPTY 슬롯이 SMA(window) 동일 anchor 공유. slot
    구별 없음.
- **slot 선정**: §4.8 — 트리거 충족 슬롯 중 가장 작은 `slot_number` 선택.
  이는 "낮은 차수부터 채운다" Phase 0 정신 그대로 (단, 매도-재진입 후엔
  sparse 패턴 자연 발생).

### 4.11 BuyEvaluationResult (사용자 검토 4차 박제)

`PriceDropStrategy.evaluate` 시그니처 교체. Phase 0의 `StrategyEvaluation`
폐기.

- **신규 ValueObject `BuyDecision`**:
  ```python
  class BuyDecision(ValueObject):
      slot_number: int            # 1..7
      target_quantity: Decimal    # lot-aligned, pre-CAUTION
      target_price: Decimal       # ReentryPriceStrategy 출력 + tick_size 정렬
      reasoning: dict[str, str]   # strategy-side reasoning (entry_price, drop_pct 등)
  ```
  Strategy 시점의 "의도". `BuyActionRecord` 와 분리되는 이유: strategy
  시점엔 broker fill 결과가 없으므로 `filled_quantity` / `filled_price` /
  `order_id` 같은 post-fill 필드를 채울 수 없음.

  대조: `SellDecision` (§5.1) ↔ `SellActionRecord` (§5.4) 의 분리와
  대칭. intent → fact 의 두 단계 모델.

- **신규 DomainModel `BuyEvaluationResult`**:
  ```python
  class BuyEvaluationResult(DomainModel):
      buy: BuyDecision | None
      skip_reason: SkipReason | None
      reasoning: dict[str, str]   # 전역 evaluation reasoning
  ```
  Invariant: `buy is not None` ⇔ `skip_reason is None` (정확히 하나만 set).

- **Orchestrator 통합 흐름**:
  ```
  result = strategy.evaluate(...)
  if result.skip_reason is not None:
      return _build_skip_decision(skip_reason=result.skip_reason, ...)
  # buy intent → CAUTION 조정 → OrderRequest → broker.place_order
  order_request = OrderRequest(slot_number=result.buy.slot_number, ...)
  fill = broker.place_order(order_request)
  # post-fill: BuyActionRecord 합성
  buy_action = BuyActionRecord(
      slot_number=result.buy.slot_number,
      split_level_after=position.split_level + 1,
      filled_quantity=fill.filled_quantity,
      filled_price=fill.filled_price,
      target_price=result.buy.target_price,
      idempotency_key=order_request.idempotency_key,
      order_id=fill.broker_order_id,
      reasoning={**result.buy.reasoning, ...},
  )
  return _build_buy_decision(buy_action=buy_action, ...)
  ```

- **`StrategyEvaluation` 운명**: 폐기. 모든 PriceDropStrategy 사용처 +
  테스트가 `BuyEvaluationResult` 로 마이그레이션.

## 5. 매도/매수 흐름

### 5.1 SellStrategy Protocol 신규

- **결정**: 매도 평가도 Strategy 분리. 매수 전략과 같은 패턴.

  ```python
  class SellStrategy(Protocol):
      def evaluate(
          self,
          *,
          position: Position,
          current_price: Price,
          config: SellStrategyConfig,
          as_of: date,
      ) -> list[SellDecision]:
          """매도 트리거된 슬롯 리스트 반환. 빈 리스트면 매도 없음."""
          ...
  ```

  - `SellDecision`: `slot_number`, `expected_price`, `reasoning: dict[str, str]`.
  - 반환이 list인 이유: 분할별 독립 매도 (§2.1) — 동시 트리거 가능.

- **`SellStrategyConfig` (DomainModel)**:
  ```python
  profit_target_pct: Decimal = Field(gt=Decimal(0), lt=Decimal(100))
  max_sells_per_day: int = Field(default=7, ge=1, le=7)
  ```

### 5.2 ProfitTargetSell — Phase 0.5 단일 구현

- **로직**: `position.slots`를 순회하며 `state == FILLED` 인 슬롯만 평가.
- 트리거: `(current_price - slot.entry.entry_price) / slot.entry.entry_price * 100 >= profit_target_pct`
- 트리거된 모든 슬롯을 SellDecision 리스트로 반환.
- `max_sells_per_day` 초과 시 `slot_number` 오름차순으로 잘라서 반환 (가장 오래된 슬롯 우선).

### 5.3 Orchestrator 흐름 (sells then buys)

- **결정**: 같은 day evaluation에서 **매도 평가 → 매도 주문 → 매수 평가 → 매수 주문** 순서.
- **이유**: 매도가 회수한 자본을 같은 날 매수가 활용 가능. 박영옥 원전의 "매도-매수 cascade" 의도와 일치.
- **신규 흐름**:
  ```
  daily_orchestrator.run_for_date(today):
    1. preflight check (잔고/포지션 등 — Phase 0와 동일)
    2. sell_actions: list[SellActionRecord] = []
       sell_decisions = sell_strategy.evaluate(...)
       for sd in sell_decisions:
         sell_order = build_sell_order(sd, position)
         result = broker.place_order(sell_order)  # OrderSide.SELL
         position = apply_sell_to_position(position, sd, result)  # slot.state=EMPTY + last_exit_* 기록
         sell_actions.append(SellActionRecord(slot_number=..., qty=..., price=..., order_id=...))
    3. buy_action: BuyActionRecord | None = None
       buy_evaluation = buy_strategy.evaluate(position, current_price, ..., reentry_price_strategy=...)
       if should_buy:
         buy_order = build_buy_order(buy_evaluation)
         result = broker.place_order(buy_order)
         position = apply_buy_to_position(position, ..., target_slot_number)
         buy_action = BuyActionRecord(slot_number=..., qty=..., price=..., order_id=...)
    4. decision = Decision(
         timestamp=..., asset=..., sell_actions=sell_actions, buy_action=buy_action,
         skip_reason=(... if both empty else None), reasoning={...},
       )
       uow.positions.save(position)
       uow.decisions.save(decision)
       uow.commit()
  ```

### 5.4 다중 액션 Decision 모델 [Schema 변경, 사용자 결정]

- **결정 (사용자 옵션 A 채택)**: 한 evaluation = 한 `Decision` row. 그러나 `Decision`은 0개 이상의 sell + 0/1개의 buy를 동시 보유 가능. "하루 1 row" 패턴 유지하면서 다중 액션 박제.

- **신규 `Decision` 필드** (Phase 0의 `action: str` 단일 필드 → 구조화 교체):

  ```python
  class SellActionRecord(ValueObject):
      slot_number: int = Field(ge=1, le=7)
      filled_quantity: Decimal = Field(gt=Decimal(0))
      filled_price: Decimal = Field(gt=Decimal(0))
      profit_pct: Decimal                  # vs entry_price
      order_id: str
      reasoning: dict[str, str]            # per-slot 매도 이유

  class BuyActionRecord(ValueObject):
      slot_number: int = Field(ge=1, le=7)
      split_level_after: int = Field(ge=1, le=7)
      filled_quantity: Decimal = Field(gt=Decimal(0))
      filled_price: Decimal = Field(gt=Decimal(0))
      target_price: Decimal                # 트리거 가격 (재진입 정책 산출)
      order_id: str
      reasoning: dict[str, str]

  class Decision(DomainModel):
      timestamp: datetime
      asset: Asset
      sell_actions: list[SellActionRecord] = []   # 0..max_sells_per_day
      buy_action: BuyActionRecord | None = None
      skip_reason: str | None = None              # 둘 다 비어있을 때만 not None
      reasoning: dict[str, str]                   # 전역 (current_price, balance 등)
  ```

  Invariants (`@model_validator`):
  - `skip_reason is not None ⇔ (len(sell_actions) == 0 AND buy_action is None)`
  - 매도 슬롯 번호 중복 금지 (`len(set(sa.slot_number for sa in sell_actions)) == len(sell_actions)`)
  - 매도 + 매수 슬롯 번호 충돌 금지 (같은 evaluation에서 슬롯 N을 팔고 동시 슬롯 N을 사는 일은 없음 — sells-then-buys 순서로 자연 보장)

- **DB schema 변경** (`SqliteDecisionRepo`):
  - 기존 `action TEXT` 컬럼 제거.
  - 신규 컬럼 `sell_actions_json TEXT NOT NULL DEFAULT '[]'`, `buy_action_json TEXT`, `skip_reason TEXT`.
  - JSON 직렬화는 Phase 0의 `PortfolioSnapshot.valuations_json` 패턴 그대로 (TypeAdapter).
  - **마이그레이션**: §3.4 정책에 따라 빈 DB로 시작. 자동 마이그레이션 코드 작성 안 함.

- **출력 호환성**:
  - `output_formatter.format_paper_decision`: 다중 액션 박스 표현으로 갱신 (예: `Sells: slot 2 (+12.3%) qty=18 px=33500 / Buys: slot 2 qty=15 px=29800`).
  - `BacktestResult.from_run` 의 `Counter(d.action for d in decisions)` 카운트 → `Counter(action_kind for d in decisions for action_kind in d._kinds())` 같은 헬퍼로 변경. `_kinds()`는 `["sell_slot_N" for sa in sells] + ["buy_split_M" if buy] + (["skip:..."] if skip)` 반환.
  - JSON 출력은 `Decision.model_dump_json()` 자동 적용 (구조화 그대로 노출).

- **이유**:
  - "한 날 1 Decision row" 패턴 유지 → 일별 회고/감사 추적이 단순.
  - 분할별 독립 매도(§2.1)의 reasoning을 슬롯 단위로 보존.
  - reasoning dict의 string-only 제약을 우회 (구조화 데이터를 dict 안 stringify로 욱여넣지 않음).
  - 결과적으로 `Decision`이 "하루의 모든 행동 단위"가 되어 의미가 더 명확.

- **블래스트 반경 (사전 식별)**:
  - `src/domain/models.py::Decision` (구조 변경) + `SellActionRecord` / `BuyActionRecord` 신규
  - `src/use_cases/daily_orchestrator.py` (Decision 생성 로직)
  - `src/infrastructure/repositories/sqlite_decision_repo.py` (schema)
  - `src/adapters/mock/in_memory_unit_of_work.py::InMemoryDecisionRepo` (호환)

### 5.4.1 reasoning 필드 운영 정책

### 5.4.2 SQLite 스키마 결정 (사용자 검토 2차 박제)

- **`decisions` 테이블 컬럼 (Phase 0.5 신규)**:
  | 컬럼 | 타입 | NULL | 비고 |
  |---|---|---|---|
  | `id` | INTEGER PK AUTOINCREMENT | NOT NULL | 그대로 |
  | `timestamp` | TEXT (ISO 8601 UTC) | NOT NULL | 그대로 |
  | `asset_fqn` | TEXT | NOT NULL | 그대로 |
  | `asset_json` | TEXT | NOT NULL | 그대로 (point-in-time 박제, ADR 0001 §8.3) |
  | `sell_actions_json` | TEXT | NOT NULL | 빈 리스트 `'[]'` 가능 |
  | `buy_action_json` | TEXT | NULL | 매수 없음일 때 NULL |
  | `skip_reason` | TEXT | NULL | sells/buy 모두 비었을 때만 not NULL |
  | `reasoning` | TEXT (JSON) | NOT NULL | 전역 reasoning dict |
- **삭제 컬럼**: 기존 `action TEXT`, `resulting_order_id TEXT` — 다중 액션 모델로 대체. `resulting_order_id`의 정보는 `SellActionRecord` / `BuyActionRecord.order_id` 안에 박제.
- **인덱스**:
  - 기존 `idx_decisions_timestamp`, `idx_decisions_asset_fqn` 유지.
  - 신규 `idx_decisions_skip_reason ON decisions(skip_reason)` — 회고 분석에서 skip 사유별 분포 집계 빈번 (예: dormant 일수 카운트). NULL 행은 인덱스에서 자동 제외 (실제 매수/매도 발생일은 빠르게 스캔에서 빠짐).
- **`SellActionRecord` / `BuyActionRecord` 안의 `idempotency_key`**:
  - **결정**: 시점 무결성 원칙 일관 (ADR 0001 §8.3 정신) — Order/Position 영속화처럼 Decision에 attached 데이터로 박제. 별도 Decision_Order 조인 테이블 만들지 않음.
  - 트레이드오프: order 테이블의 row를 Decision에서 참조하려면 `idempotency_key`로 join 필요 (FK 아님). 정상 운영에서는 6개월 뒤 디버그용 join이라 충분.
- **마이그레이션 정책**: ADR 0002 §3.4 그대로 — 빈 DB로 시작. 자동 변환 스크립트 작성하지 않음.

### 5.5 Invariants 명세 (사용자 검토 2차 박제)

`Decision.@model_validator(mode="after")`로 강제. 위반 시 `ValidationError`.

1. **Invariant 1 — skip ⇔ both empty**:
   - `skip_reason is not None` ⇔ `len(sell_actions) == 0 AND buy_action is None`
   - 양 방향 동시 강제 (skip이 있으면 sells/buy 비어있어야 하고, 비어있으면 skip 필수).
   - 이유: "결정 없음 = 결정함" — Decision이 sells/buy 모두 비어있으면 사유가 반드시 박제되어야 시점 추적 가능.

2. **Invariant 2 — sell slot uniqueness**:
   - `len({sa.slot_number for sa in sell_actions}) == len(sell_actions)`
   - 같은 evaluation에서 슬롯 N을 두 번 매도하는 일 불가능 (슬롯은 한 번만 매도되면 EMPTY).

3. **Invariant 3 — sell ↔ buy slot 충돌 금지**:
   - `buy_action is not None` 이면 `buy_action.slot_number not in {sa.slot_number for sa in sell_actions}`
   - sells-then-buys 순서에서 자연 보장되지만 (매도 후 EMPTY → 가장 작은 EMPTY는 다른 번호일 가능성 큼), 정책 D가 매도 직후 같은 슬롯 재진입을 시도하는 엣지 케이스 차단.

추가 (warning 수준, 강제는 안 함):
- per-action `reasoning`에 `slot_number` / `entry_price` (sell) / `target_price` (buy) 박제 권장.

### 5.6 SkipReason enum 확장 (사용자 검토 2차 박제)

Phase 0 ADR 0001 §6에 박제된 9개 SkipReason은 그대로 유지. Phase 0.5에서 회고 분석 보강 차원으로 다음 3개 추가:

| 신규 enum 값 | 발화 조건 | 회고 분석 의미 |
|---|---|---|
| `NO_ACTION_TAKEN` | 매도/매수 평가 모두 트리거 없음 (general fallback) | "전략이 정말 아무 것도 안 함" 일 수 (포괄 카테고리) |
| `ALL_SLOTS_EMPTY_NO_TRIGGER` | 모든 슬롯 EMPTY (첫 매수 대기) + 첫 매수 트리거 미발화 | 시스템 시작 직후 "데이터 부족 / 잘못된 fixture" 같은 패턴 추적용 |
| `ALL_SLOTS_FILLED_NO_PROFIT` | 모든 슬롯 FILLED + 매도 임계치 미달 | Phase 0의 4.7년 dormancy 원인 — 자본 100 % 사용 + 회복 안 됨. Phase 0.5의 **자본 회전율 KPI 분모** |
| `INSUFFICIENT_HISTORICAL_DATA` (§4.10) | 모든 평가 가능한 빈 슬롯의 trigger 계산이 데이터 부족(`None`)으로 실패 | MovingAverageReentry window 미충족 (시스템 시작 직후 N일 미만). 백테스트 시작점 + N일 이전 구간 분석에서 자동 제외 가능 |
| `ALL_EMPTY_SLOTS_EXCLUDED_BY_SAME_DAY_SELL` (§5.9.3) | 같은 evaluation에서 매도 발생 후 모든 EMPTY 슬롯이 sell된 슬롯과 충돌 | §5.5 Invariant 3 자연 보장 메커니즘. 7-FILLED → all sold + 같은 날 D-2 매수 트리거의 매우 드문 케이스 추적용 |

기존 `STRATEGY_NO_BUY` 는 매수 평가에서 should_buy=False 반환 시 사용 (slot 상태 무관). Phase 0.5에서:
- 매수만 있고 매도 없는 흐름이면 기존 분기 유지.
- 매수+매도 모두 트리거 없음이면 위 3개 중 정확한 사유 박제.

분류 우선순위 (순회 매도-then-매수 후 평가):
1. sells/buy 둘 다 있음 → skip_reason = None
2. all FILLED + 매도 미발화 → `ALL_SLOTS_FILLED_NO_PROFIT`
3. all EMPTY + 매수 미발화 → `ALL_SLOTS_EMPTY_NO_TRIGGER`
4. 그 외 (혼재 + 트리거 없음) → 매수 평가 사유 우선 (`STRATEGY_NO_BUY` 또는 더 구체적인 기존 enum)

### 5.9 sell-buy 통합 결정 (사용자 검토 6차 박제)

§5.3 sells-then-buys cascade 흐름의 세부 정책을 박제. 0.5.14
DailyOrchestrator 통합 직전 결정.

#### 5.9.1 Idempotency key 스킴 [결정 1A]

- **결정**: 모든 주문 key 에 슬롯 식별자 포함.
  - SELL: `{asset.fqn}:{date}:sell:{slot_number}` (예: `KRX:069500:2026-04-30:sell:3`)
  - BUY: `{asset.fqn}:{date}:buy:{slot_number}` (예: `KRX:069500:2026-04-30:buy:1`)

- **이유**:
  - 한 evaluation에 SELL N건 + BUY 1건 가능 → 순번형(0/1/2…) 보다 슬롯 ID
    가 결정적. 재시도 시 같은 슬롯 = 같은 key (CLAUDE.md §4.1 idempotency
    정신 그대로).
  - 박영옥 sparse 패턴(§3.3) 호환 — 같은 날 슬롯 2 매도, 다음날 슬롯 2 재매수
    시 date 차이로 자연 분리.
  - 통일성: BUY/SELL 모두 동일 형식 → 운영/디버그 단순.

- **변경 영향**: Phase 0의 BUY key `{fqn}:{date}` → `{fqn}:{date}:buy:{slot_number}`.
  Phase 0 백테스트 fixture 는 §3.4 정책에 따라 빈 DB로 시작이라 호환 문제 없음.

#### 5.9.2 Signal level 의 SELL 처리 [결정 2A]

- **결정 (Phase 0.5 한정)**: `HALT` / `EMERGENCY` 신호는 sells/buys 양쪽 모두
  차단. `CAUTION` 은 BUY 수량만 절반 (Phase 0 동작 유지), SELL 은 풀 수량.

- **이유**:
  - Phase 0.5 는 NullSignal 만 사용 → 사실상 무관.
  - Phase 0 정책 일관성. 결정 변수 늘리지 않음.
  - `SignalLevel` docstring "HALT=block new entries, EMERGENCY=reduce existing
    positions" 정신은 Phase 1+ RuleBasedSignal 도입 시 §5.x 신규 라운드에서
    정정.

- **재검토**: Phase 1+ ADR (RuleBasedSignal 도입 시).

#### 5.9.3 Same-day rebuy 차단 메커니즘 [결정 3A]

§5.5 Invariant 3 (`buy_slot ∉ sell_slots`) 을 자연 위반 가능한 케이스 박제:
7-FILLED 상태에서 슬롯 N 매도 → D-2 (MA-based) 가 같은 날 동일 슬롯 N에
재매수 트리거.

- **결정**: `PriceDropStrategy.evaluate` 시그니처에 `excluded_slot_numbers:
  set[int] | None = None` 파라미터 추가. orchestrator 는 sells 완료 후
  `set(sa.slot_number for sa in sell_actions)` 를 주입.

- **PriceDropStrategy 책임**:
  - `excluded_slot_numbers` 가 `None` / 빈 set → 기존 동작 그대로.
  - candidate_slots 에서 `slot_number ∈ excluded_slot_numbers` 슬롯 제거.
  - 모든 EMPTY 슬롯이 제거되면 → `BuyEvaluationResult(skip_reason=
    ALL_EMPTY_SLOTS_EXCLUDED_BY_SAME_DAY_SELL)`.

- **ReentryPriceStrategyPort 변경 없음**: 필터링은 PriceDropStrategy 내부.

- **Default**: `None` (기존 호출자 호환). orchestrator 만 명시 주입.

- **이유**:
  - Strategy 가 사실을 알고 결정 — 가장 단순. Decision invariant 는 안전망 유지.
  - `excluded_slot_numbers` 의 의미는 "이번 evaluation 에서 평가 제외할 슬롯".
    Phase 1+ 다른 사유 (점검 모드, manual hold 등) 도 같은 패러다임으로 확장.

- **신규 SkipReason `ALL_EMPTY_SLOTS_EXCLUDED_BY_SAME_DAY_SELL`**: §5.6 표
  갱신.

- **OrderRequest 갱신 (decision 3A 후속)**: 0.5.14 구현 중 발견된 gap —
  `OrderRequest` 의 BUY invariant `slot_number must be None` 가 strategy 의
  slot 의도를 broker 까지 전달하지 못함 (broker 는 항상 "smallest EMPTY"
  로 채움 → 같은 날 매도된 slot 1 에 즉시 재매수 → Decision Invariant 3
  자연 위반). 이를 해결하기 위해 BUY 도 `slot_number` 를 명시 가능하도록
  invariant 완화:

  | side | 갱신 전 | 갱신 후 |
  |---|---|---|
  | BUY  | `slot_number` 반드시 None | `slot_number` 선택 (지정 시 broker 가 그 slot 에 fill, None 시 smallest EMPTY) |
  | SELL | `slot_number` 필수      | 변경 없음 |

  Strategy 가 결정한 slot (`BuyDecision.slot_number`) 이 그대로 broker
  까지 전달되어, broker 가 strategy 의 의도와 어긋난 slot 을 채우지
  않는다. backward-compat 안전 — slot_number=None 시 Phase 0 동작 그대로.

#### 5.9.4 Sell 주문 실패 처리

§5.3 흐름 중 N개 sells 주문 중 일부 실패 시:

- **결정**: sell 루프에서 첫 `BrokerConnectionError` / `BrokerOrderError` 발생
  시 그 시점에서 sells 중단 + 이미 성공한 sells 박제 + buy 평가 생략.

- **상세 분기**:
  - sells 일부 성공 + 한 건 실패 → 성공한 sells 박제 (`Decision.sell_actions`),
    buy 생략. `Decision.skip_reason` 은 None (Invariant 1: sells 비어있지
    않으므로). 실패 사실은 `Decision.reasoning` 에 `sell_loop_aborted_at_slot=N`
    + `sell_loop_error=...` 박제.
  - sells 0건 성공 + 첫 sell 실패 → sells=[], buy 생략, skip_reason=
    `BROKER_REJECTED` (BrokerOrderError) 또는 `BROKER_TIMEOUT`
    (BrokerConnectionError).
  - sells 모두 성공 + buy 단계에서 실패 → sells 박제 + buy 생략 (skip_reason
    None, sells 박제 사실로 충분).

- **이유**:
  - 단순성 우선. 부분 실패 후 buy 시도하면 자본/포지션 일관성 추적이 폭증.
  - 이미 fill 된 sells 는 broker DB 에 박혔으므로 박제 의무.

- **재검토**: Phase 1 KIS API 진입 시 — 실 sell 부분 실패 발생 시 더 정교한
  retry/skip 정책 필요.

  - `AssetStrategyBundle` (DomainModel): asset, buy_config, sell_config, reentry_config (모두 pydantic 검증).
- **검증**:
  - 누락 키 → ValidationError
  - 알 수 없는 strategy 이름 → ValueError
  - 파라미터 범위 (`profit_target_pct ∈ (0, 100)`, `cooldown_days ∈ [0, 365]`)
  - reentry_strategy 와 reentry_parameters 일관성:
    - `current_market` 인데 `cooldown_days` 명시 → warning (사용 안 됨)
    - `hybrid` 인데 `cooldown_days` 누락 → ValidationError
- **Phase 0.5 단일 자산 가정**: dict의 첫 키만 사용. 멀티 자산은 Phase 0.7.

### 6.3 CLI `--config` 옵션 (mutually exclusive 정책)

- **결정**: `trading backtest` / `trading paper` 양쪽에 `--config PATH`
  옵션 추가. `--config`와 **strategy 파라미터 flag**는 **mutually exclusive** — 동시에 지정 시 `click.UsageError` 로 즉시 거부.
- **strategy 파라미터 flag 정의** (거부 대상):
  - `--drop-pct`, `--max-split`, `--per-split-amount`, `--max-split-per-day`
  - (Phase 0.5 신규) `--profit-target-pct`, `--max-sells-per-day`, `--reentry-strategy`, `--cooldown-days`
- **메타 옵션 (함께 허용)**:
  - `--csv`, `--start`, `--end`, `--date`, `--db`, `--capital`, `--json`
  - 이유: 메타는 실행 환경 기술 (어디서/언제/얼마로). 전략 본질이 아님.
- **거부 메시지 예시**:
  ```
  Error: --config and strategy flags (--drop-pct, --max-split, ...) are mutually exclusive.
  Either pass --config PATH (recommended for reproducibility) or use the flag-only form.
  ```
- **이유**:
  - **명확성**: 같은 파라미터를 두 곳에서 지정하면 어느 게 우선인지 README 없이 알 수 없음.
  - **재현성**: 백테스트 결과 박제 시 "이 명령으로 재현"이 단순 — config 파일 + 메타 옵션만.
  - **Data Snooping 방지** (§6.5): flag 빠르게 바꿔가며 튜닝하는 유혹 차단. config 변경은 git diff 박제 동반.
  - **자동화 친화**: `trading backtest --config xxx.yaml` 한 줄로 모든 전략 파라미터 결정.
- **`--config` 미지정 + flag 사용 → Phase 0 호환 흐름 그대로** (regression 회피).
- **`trading config validate --config PATH`**: 신규 명령. 로더만 호출하여 검증 결과 출력 (실행은 안 함).

### 6.4 Hot reload 미도입 (재확인)

- Phase 0.5 미도입. 시스템 재시작이 설정 변경 적용 메커니즘.
- Phase 1 실거래 진입 후 검토.

### 6.5 Data Snooping 방지 재강조

YAML 파라미터가 5분 안에 변경 가능해지면서 무분별 튜닝 유혹 증가.
Phase 0 ADR (없으면 본 ADR §6.5에 박제) 정책 적용:
1. 파라미터 변경 전 **가설 명시** ("왜 이 값이 더 좋을 것 같은가?")
2. 한 번에 1~2개 변수만 변경
3. ADR에 변경 이유 박제
4. 결과 안 좋으면 원복. "혹시 더 잘 맞는 값" 무한 탐색 금지

Phase 0.5 백테스트는 D vs F 정책 비교가 핵심. 파라미터 (`profit_target_pct`,
`cooldown_days`, `drop_threshold_pct`) 튜닝은 별도 작업.

## 7. Phase 0.7 호환성 (CLAUDE.md §16 신규 룰)

### 7.0 동기

Phase 0.5는 단일 종목 작업이지만, Phase 0.7에서 멀티 종목 확장 예정.

1. **asset 단위 처리 로직 분리**: `DailyOrchestrator.run_for_date(today)`는
   `_run_for_asset(asset, config, today)` 호출하는 wrapper로.
2. **단일 asset 시그니처 유지하되 내부 loop-ready**: `__init__`은
   `asset: Asset` 단수 그대로. 내부에서 `[self.asset]` 처럼 list로 감싸 처리해도 OK.
3. **config / position 종목별 독립 처리**: 이미 `SplitStrategyConfig`,
   `Position`이 종목별 독립 (변경 불필요).

### 7.2 금지

- 종목 간 자본 배분 정책 코드
- 종목 우선순위 코드
- 종목 간 자본 이동 코드
- "멀티 종목 대비 추상화"라는 이름의 미리 짠 디자인

→ Phase 0.7 ADR 라운드에서 사용자와 명시적 결정 후 작성.

## 8. 백테스트 비교 계획

### 8.1 측정 지표

| 지표 | 산출 방법 | 의미 |
|---|---|---|
| Total return | `(final_value / initial - 1) × 100` | 절대 수익 |
| CAGR | metrics.cagr | 연 환산 |
| MDD | metrics.max_drawdown | 위험 |
| Sharpe | metrics.sharpe_ratio (rf=0) | 위험조정수익 |
| Calmar | metrics.calmar_ratio | CAGR/|MDD| |
| **자본 회전율 (신규)** | `누적 buy 금액 / initial_capital × (252 / N_days)` | 자본 활용 적극성 |
| **누적 매도 횟수 (신규)** | `count(action.startswith("sell_"))` | 익절 발화 빈도 |
| **평균 자본 활용률 (신규)** | `mean(committed_capital_t / initial_capital for t in days)` | 시간평균 자본 활용 |

신규 3개 지표는 Phase 0.5 회고 분석 스크립트에서 계산 (BacktestResult 빌트인은 Phase 1에서 검토).

### 8.2 비교 대상 (3-way)

| 시나리오 | 매수 | 매도 | 재진입 | config |
|---|---|---|---|---|
| Phase 0 (baseline) | PriceDrop split×7 | 없음 | 없음 | (Phase 0 결과 인용) |
| Phase 0.5 D | PriceDrop split×7 | ProfitTarget +10% | CurrentMarketReentry | `strategies-D.yaml` |
| Phase 0.5 F | PriceDrop split×7 | ProfitTarget +10% | HybridTimeBasedReentry (cooldown=60) | `strategies-F.yaml` |

### 8.3 동일 입력 조건

- 데이터: `data/historical/KRX_069500_2020-2024.csv` (Phase 0 retrospective와 동일)
- 기간: 2020-01-02 ~ 2024-12-30 (1231 거래일)
- 초기 자본: 100,000,000 KRW
- per_split_amount: 10,000,000 KRW
- drop_threshold_pct: 5.0 %
- max_split_count: 7
- profit_target_pct: 10.0 %

### 8.4 자동화 흐름

```bash
trading backtest --config config/strategies-D.yaml \
  --csv data/historical/KRX_069500_2020-2024.csv \
  --start 2020-01-02 --end 2024-12-30 --json > /tmp/D.json

trading backtest --config config/strategies-F.yaml \
  --csv data/historical/KRX_069500_2020-2024.csv \
  --start 2020-01-02 --end 2024-12-30 --json > /tmp/F.json

uv run python scripts/compare_phase05.py /tmp/D.json /tmp/F.json
```

`scripts/compare_phase05.py` 는 Phase 0.5 retrospective 분석 산출물.
Phase 0.7+에서 재사용 가능.
