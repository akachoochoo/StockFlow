## 1. Phase 0.5 목적

### 1.0 배경

Phase 0 회고(`docs/retrospectives/phase-0.md` §3.4)에서 5년 KOSPI 200
백테스트 결과 핵심 한계로 부각:

> 7회 분할 모두 COVID 1차 충격(2020-01~03 76일) 안에 발화 → 이후 4.7년
> dormancy. 매도 로직 부재가 가장 큰 기회비용.

전략의 +4.82pp 초과수익(B&H 대비)이 진정한 알파인지, 아니면 단지 COVID
저점 매수의 우연인지 판별할 유일한 방법은 **매도 로직 추가 후 재백테스트**.
회복기에 익절하고 회수된 자본이 다음 변동성에 재투입되는 흐름이 작동
하는지가 핵심 검증 지점.

### 1.1 Phase 분할 결정

| Phase | 범위 | 목적 |
|---|---|---|
| **Phase 0.5** | 매도 로직 + 재진입 (단일 종목) | 매도 효과 단독 검증 |
| Phase 0.7 | 멀티 종목 + 자본 배분 | 종목 다변화 효과 단독 검증 |
| Phase 1 | KIS API + 모의투자 + 매도 텔레그램 | 실거래 진입 |

**분할 이유:** 변수 분리 측정. 매도와 멀티 종목을 한 phase에 묶으면
"어느 변경이 결과를 만들었나" 판별 불가능. 한 번에 한 변수 (CLAUDE.md
§13.1 "추측하지 말 것" 정신).

### 1.2 Phase 0.5 완료 조건 (선언적)

§10에서 운영 기준으로 상세화. 본 §1.2는 비전:
- 매도가 작동한다 (분할별 독립 +10% 익절)
- 재진입이 작동한다 (D, F 두 정책 양쪽)
- 백테스트 ↔ 페이퍼 동일성 invariant 여전히 유지
- D vs F 5년 비교 결과 박제 + Phase 0.5 회고 작성

### 1.3 가설 (Hypothesis)

**핵심 가설:** Phase 0의 +4.82pp 초과수익 중 일부는 우연(COVID 저점 매수의
타이밍 효과)이고, 매도 + 재진입 도입 시:

- **H1 (자본 회전 알파)**: 회수된 자본이 후속 변동성에 재투입되면서 Phase 0 baseline 대비 **자본 회전율이 N배 이상 증가**한다 (N ≥ 2 가정).
- **H2 (총 수익 우월)**: 정책 D 또는 F 중 적어도 하나가 Phase 0 baseline의 +25.96 % 총 수익을 능가한다.
- **H3 (위험조정 수익 유지/개선)**: Sharpe ratio가 Phase 0의 0.39 대비 ≥ 0.39 (위험조정 수익 악화 없음).
- **H4 (D vs F 차별화)**: D와 F의 결과가 measurably 다르다 (단순 노이즈 수준 이상). 차이가 미미하다면 추가 정책 다양성은 Phase 0.7+로 미룬다.

### 1.4 반증 기준 (Falsifiability)

각 가설이 **거짓**으로 드러나는 경계:

| 가설 | 거짓 판정 조건 | Phase 0.5 액션 |
|---|---|---|
| H1 | 자본 회전율이 Phase 0 대비 2배 미만 | 매도 임계치 또는 재진입 정책 가정 재검토 |
| H2 | D, F 둘 다 Phase 0 baseline 미달 | 매도 임계치(+10%) 자체 재검토 (회고 ADR §12 신규) |
| H3 | Sharpe < 0.30 (악화) | 매도가 변동성을 가산했음 — 손절 도입 우선순위 상승 |
| H4 | D, F 결과 차이 ≤ 1pp (return) AND ≤ 5% (회전율) | Phase 0.5 단일 정책 채택 + 추가 정책 Phase 1+ |

H1·H2·H3 모두 거짓이면 Phase 0.5의 결론은 "매도 도입 무용 또는 해롭다"
가 되며, Phase 0.5 회고 §7에서 Phase 1 KIS API 직진 권고 (매도 보류).

### 1.5 Phase 0.7 진입 기준

다음 게이트 모두 통과 시 Phase 0.7 진입 가능:

1. ✅ Phase 0.5 §10 완료 게이트 4건 모두 통과 (코드 품질, invariant, 실데이터, 회고)
2. ✅ H1·H2·H3 중 ≥ 2 가설이 참 (즉, 매도가 가치 추가)
3. ✅ Phase 0.5 회고에서 사용자 + AI가 **D 또는 F 중 하나를 default로 채택** 결정 박제
4. ✅ 멀티 종목 도입 시 우려 사항 (자본 배분, 동시 매수 시 idempotency 충돌, 종목 우선순위) 식별 + Phase 0.7 ADR 라운드 트리거

## 2. 매도 정책

### 2.1 분할별 독립 매도 (박영옥 원전)

- **결정**: 7개 분할 슬롯 각각이 독립적으로 매도 평가. 한 슬롯이 매도
  조건 충족하면 해당 슬롯만 매도, 다른 슬롯은 영향 없음.
- **이유**: 박영옥 "주식투자 절대지식"의 7분할 매매 원전이 분할별 독립
  관리. 평단가 기준 매도(전체 포지션 일괄)와 다른 패러다임 — 분할별
  독립이 자본 회전과 추적 가능성에서 우위.
- **트레이드오프**: 부분 매도라 수수료 누적 증가. Phase 0 Mock에서는
  수수료 0이라 무관. Phase 1 KIS API 도입 시 수수료 모델 추가.

### 2.2 매도 임계치 (단순 +10 %)

- **결정**: 각 슬롯 `entry_price` 대비 `current_price` 가 +`profit_target_pct` (기본 10.0) 이상이면 매도 트리거.
- **모든 슬롯 동일 임계치** — 슬롯별 차등 임계치는 Phase 0.5 제외 (Phase 0.7 회고 후 재검토).
- **이유**: Phase 0.5는 "매도가 작동하는가" 검증이 목표. 임계치 튜닝은
  변수가 늘어나 검증 노이즈. 박영옥 원전도 단순 % 기준.
- **트레이드오프**: 횡보장에서 +10% 도달 못 하면 매도 안 됨 → 매수만
  하는 Phase 0와 동일 거동. 의도된 단순성.

### 2.3 동시 트리거 처리

- **결정**: 한 evaluation에서 N개 슬롯이 동시 매도 트리거되면 **모두
  매도**. 우선순위 없음.
- **이유**: 우선순위 정책 도입은 또 하나의 변수. 단순성 우선.

### 2.4 부분 매도 불가

- **결정**: 한 슬롯은 통째로 매도하거나 안 함. 슬롯 안 50 % 매도 등의
  세분화 없음.
- **이유**: 슬롯이 이미 분할 단위. 추가 분할은 복잡성 폭증.
- **재검토**: Phase 1+에서 RuleBasedSignal이 부분 매도 신호를 보낼
  경우 재고.

### 2.5 손절 미도입 (Phase 0.5)

- **결정**: 평단 기준 -X % 손절 정책 **Phase 0.5에서 도입 안 함**.
- **이유**: Phase 0.5는 익절 + 재진입의 알파만 측정하는 게 목적. 손절
  추가는 또 하나의 변수. 박영옥 원전도 손절 강제 안 함 (오히려 분할
  매수 강도 증가로 평단 낮춤).
- **CLAUDE.md §11.4 정책**: "추가 매수 자동 정지 + 사람 개입 대기"는
  유지 (max_loss_pct 도달 시).
- **재검토**: Phase 1 실거래 진입 시 — Mock 백테스트와 실거래의
  최대 차이는 최악 시나리오 보호. 손절은 그 때 필수 검토.

## 3. 슬롯 모델 도입

### 3.1 SplitSlot 값 객체

- **결정**: 새 ValueObject `SplitSlot` 도입. 7개 고정 슬롯이 매도/재진입
  사이클을 거치며 EMPTY ↔ FILLED 전환.

  ```python
  class SplitSlot(ValueObject):
      slot_number: int = Field(ge=1, le=7)        # 고정, 1..7
      state: SlotState                              # EMPTY | FILLED
      entry: SplitEntry | None                      # FILLED일 때만 not None
      last_exit_price: Decimal | None               # 직전 매도가 (재진입 정책 F용)
      last_exit_date: date | None                   # 직전 매도일 (cooldown 계산용)
  ```

  Invariants (`@model_validator`):
  - `state == FILLED ⇔ entry is not None`
  - `state == EMPTY ⇒ entry is None` (그러나 last_exit_* 는 가능 — 재진입 대기 슬롯)
  - `last_exit_date is not None ⇒ last_exit_price is not None`

- **`SlotState` enum**: `EMPTY` / `FILLED`.

### 3.2 Position 마이그레이션 (entries → slots)

- **결정**: `Position.entries: list[SplitEntry]` 제거. `Position.slots: list[SplitSlot]` 신규.
- **`split_level` 의미 변경**: "채워진 슬롯 개수" = `sum(1 for s in slots if s.state == FILLED)`. 매도 시 감소 가능.
- **신규 invariants**:
  - `len(slots) == max_split_count` (Phase 0.5: 7로 고정)
  - `slot_number` 1..N 연속, 정렬 보장
  - `quantity == sum(s.entry.quantity for s in slots if s.state == FILLED)`
  - `avg_price == weighted_avg(s.entry.entry_price * s.entry.quantity for FILLED slots)` (정확 일치, Phase 0의 5개 invariant 중 1개 그대로)
  - `quantity == 0 ⇒ split_level == 0` 그러나 last_exit_* 는 보존 가능
- **마이그레이션 영향 범위 (사전 식별)**:
  - `src/domain/models.py::Position` 본체
  - `src/domain/strategies/price_drop.py` (entries 참조)
  - `src/use_cases/daily_orchestrator.py`
  - `src/adapters/mock/broker.py::_update_position` (entries 추가/갱신 로직)
  - `src/infrastructure/repositories/sqlite_position_repo.py` (저장 schema)
  - `src/application/snapshot_builder.py` / `backtest_runner.py` (참조 가능성)
  - 모든 관련 단위 + 통합 테스트

### 3.2.1 부분 체결 차단 정책 (Phase 0.5 한정)

- **결정**: Phase 0.5에서 **부분 체결을 BUY/SELL 양쪽에 대해 차단**.
  - `MockBroker.__init__`: `simulate_partial_fill_rate=0.0` 강제 (생성자에서 0이 아닌 값을 받으면 raise).
  - `BacktestRunner` / paper composition root에서 MockBroker 생성 시 옵션 노출 안 함.
- **이유 (강화)**:
  - §3.2 invariant 강화 (`quantity == sum(...)` 등호화)와 일관 — partial fill carry 의 도메인 모델이 사라졌으므로 broker도 발생시킬 수 없게 차단.
  - 부분 매도 모델 부재(§5.6)와도 대칭. BUY만 partial 허용하면 슬롯 무결성 깨짐.
  - Phase 0.5의 검증 목표는 "매도/재진입 정책 알파 측정". partial fill 노이즈는 측정을 흐림.
- **Phase 1 KIS 본격화**:
  - 실 KIS API는 partial fill을 자연스럽게 발생시킴.
  - Phase 1 진입 직전 별도 ADR 라운드에서:
    - 부분 체결 도메인 모델 부활 (혹은 새 설계)
    - 슬롯 invariant 완화 (`quantity == sum + pending_carry`)
    - 부분 매도 정책 (재시도 vs 큰 슬롯 분할 vs reject)
- **재검토**: Phase 1 ADR §1 (KIS API 도입 시).

### 3.3 sparse split_number 허용

- **결정**: 매도/재진입 반복 시 `slot_number=2`가 EMPTY인 채 `slot_number=3`이 FILLED인 상태 정상.
- **이유**: 박영옥 원전의 "각 슬롯이 자기 사이클을 가짐" 패러다임 박제.
- **`SplitEntry.split_number`**: Phase 0의 `1, 2, …, split_level` 연속 invariant **제거**. 이제 슬롯 식별자.

### 3.4 데이터 마이그레이션 정책

- **결정**: Phase 0 SQLite 스키마와 호환되지 않음. **빈 DB로 시작**.
- **이유**: Phase 0 데이터는 검증용 fixture지 운영 자산 아님 (회고 §1).
  실거래 데이터 마이그레이션은 Phase 1 진입 직전 별도 ADR 라운드.
- **박제할 것**: 본 §3.4와 함께 "Phase 0 → Phase 1 운영 전환 시
  마이그레이션 스크립트는 별도 ADR 라운드"라는 정책. 자동 마이그레이션
  코드는 Phase 0.5에서 작성 안 함.

## 4. 재진입 가격 정책

### 4.1 ReentryPriceStrategy Protocol

- **결정**: 재진입 트리거 가격 계산을 Strategy 패턴으로 분리.

  ```python
  class ReentryPriceStrategy(Protocol):
      def get_trigger_price(
          self,
          *,
          slot: SplitSlot,
          position: Position,
          current_price: Decimal,
          drop_threshold_pct: Decimal,
          as_of: date,
      ) -> Decimal:
          """빈 슬롯 재진입 트리거 가격을 반환."""
          ...
  ```

- **이유**: 정책 D, F 비교가 Phase 0.5 핵심 검증. Strategy 분리로
  비교 자동화 + 향후 신규 정책 추가 시 인터페이스 안정성.

### 4.2 정책 D — `CurrentMarketReentry`

- **공식**: `trigger_price = current_price × (1 - drop_threshold_pct/100)`
- **특징**: 빈 슬롯이라면 매도 이력 무시. 항상 시장가 기준.
- **장점**: 우상향 추세에서도 일상 변동성 활용. 자본 회전 적극적.
- **단점**: 매도 직후 재진입 가능성 높음 → "팔자마자 다시 사기" 시나리오.

### 4.3 정책 F — `HybridTimeBasedReentry`

- **파라미터**: `cooldown_days` (기본 60).
- **공식**:
  - `last_exit_date` 없음 (시스템 시작 직후 빈 슬롯) → D와 동일 (`current_price` 기준)
  - `(as_of - last_exit_date).days < cooldown_days` → `last_exit_price × (1 - drop_threshold_pct/100)`
  - `(as_of - last_exit_date).days >= cooldown_days` → `current_price × (1 - drop_threshold_pct/100)` (D와 동일)
- **장점**: 직후 보수적 (재매수 회피), 시간 흐르면 D처럼 회전 활성화.
- **단점**: cooldown 동안 큰 추가 하락이 와도 재진입 못 함 (last_exit_price - X% 깊은 곳까지 가야).

### 4.4 매수 전략과의 결합

- **결정**: `PriceDropStrategy` 가 `ReentryPriceStrategy` 를 의존성으로
  주입받음. 첫 매수(position=None)는 기존 로직 그대로 (current_price 즉시
  매수). 빈 슬롯 재진입은 `ReentryPriceStrategy.get_trigger_price()` 활용.
- **시그니처 변경**:
  ```python
  PriceDropStrategy(reentry_price_strategy: ReentryPriceStrategy)
  ```
- **단일 슬롯이 EMPTY인 케이스**: 가장 작은 빈 `slot_number` 슬롯에
  매수 (slot_number 우선순위). 동시 여러 슬롯 매수 가능 (`max_split_per_day`
  허용 범위 내, ADR 0001 §7.11 그대로).

### 4.5 정책 비교 백테스트 — 측정 지표

§8에서 상세화. 핵심 추가 지표: **자본 회전율**, **누적 매도 횟수**,
**평균 자본 활용률**.

## 5. 매도/매수 흐름

### 5.1 SellStrategy Protocol 신규

- **결정**: 매도 평가도 Strategy 분리. 매수 전략과 같은 패턴.

  ```python
  class SellStrategy(Protocol):
      def evaluate(
          self,
          *,
          position: Position,
          current_price: Price,
          config: SellStrategyConfig,
          as_of: date,
      ) -> list[SellDecision]:
          """매도 트리거된 슬롯 리스트 반환. 빈 리스트면 매도 없음."""
          ...
  ```

  - `SellDecision`: `slot_number`, `expected_price`, `reasoning: dict[str, str]`.
  - 반환이 list인 이유: 분할별 독립 매도 (§2.1) — 동시 트리거 가능.

- **`SellStrategyConfig` (DomainModel)**:
  ```python
  profit_target_pct: Decimal = Field(gt=Decimal(0), lt=Decimal(100))
  max_sells_per_day: int = Field(default=7, ge=1, le=7)
  ```

### 5.2 ProfitTargetSell — Phase 0.5 단일 구현

- **로직**: `position.slots`를 순회하며 `state == FILLED` 인 슬롯만 평가.
- 트리거: `(current_price - slot.entry.entry_price) / slot.entry.entry_price * 100 >= profit_target_pct`
- 트리거된 모든 슬롯을 SellDecision 리스트로 반환.
- `max_sells_per_day` 초과 시 `slot_number` 오름차순으로 잘라서 반환 (가장 오래된 슬롯 우선).

### 5.3 Orchestrator 흐름 (sells then buys)

- **결정**: 같은 day evaluation에서 **매도 평가 → 매도 주문 → 매수 평가 → 매수 주문** 순서.
- **이유**: 매도가 회수한 자본을 같은 날 매수가 활용 가능. 박영옥 원전의 "매도-매수 cascade" 의도와 일치.
- **신규 흐름**:
  ```
  daily_orchestrator.run_for_date(today):
    1. preflight check (잔고/포지션 등 — Phase 0와 동일)
    2. sell_actions: list[SellActionRecord] = []
       sell_decisions = sell_strategy.evaluate(...)
       for sd in sell_decisions:
         sell_order = build_sell_order(sd, position)
         result = broker.place_order(sell_order)  # OrderSide.SELL
         position = apply_sell_to_position(position, sd, result)  # slot.state=EMPTY + last_exit_* 기록
         sell_actions.append(SellActionRecord(slot_number=..., qty=..., price=..., order_id=...))
    3. buy_action: BuyActionRecord | None = None
       buy_evaluation = buy_strategy.evaluate(position, current_price, ..., reentry_price_strategy=...)
       if should_buy:
         buy_order = build_buy_order(buy_evaluation)
         result = broker.place_order(buy_order)
         position = apply_buy_to_position(position, ..., target_slot_number)
         buy_action = BuyActionRecord(slot_number=..., qty=..., price=..., order_id=...)
    4. decision = Decision(
         timestamp=..., asset=..., sell_actions=sell_actions, buy_action=buy_action,
         skip_reason=(... if both empty else None), reasoning={...},
       )
       uow.positions.save(position)
       uow.decisions.save(decision)
       uow.commit()
  ```

### 5.4 다중 액션 Decision 모델 [Schema 변경, 사용자 결정]

- **결정 (사용자 옵션 A 채택)**: 한 evaluation = 한 `Decision` row. 그러나 `Decision`은 0개 이상의 sell + 0/1개의 buy를 동시 보유 가능. "하루 1 row" 패턴 유지하면서 다중 액션 박제.

- **신규 `Decision` 필드** (Phase 0의 `action: str` 단일 필드 → 구조화 교체):

  ```python
  class SellActionRecord(ValueObject):
      slot_number: int = Field(ge=1, le=7)
      filled_quantity: Decimal = Field(gt=Decimal(0))
      filled_price: Decimal = Field(gt=Decimal(0))
      profit_pct: Decimal                  # vs entry_price
      order_id: str
      reasoning: dict[str, str]            # per-slot 매도 이유

  class BuyActionRecord(ValueObject):
      slot_number: int = Field(ge=1, le=7)
      split_level_after: int = Field(ge=1, le=7)
      filled_quantity: Decimal = Field(gt=Decimal(0))
      filled_price: Decimal = Field(gt=Decimal(0))
      target_price: Decimal                # 트리거 가격 (재진입 정책 산출)
      order_id: str
      reasoning: dict[str, str]

  class Decision(DomainModel):
      timestamp: datetime
      asset: Asset
      sell_actions: list[SellActionRecord] = []   # 0..max_sells_per_day
      buy_action: BuyActionRecord | None = None
      skip_reason: str | None = None              # 둘 다 비어있을 때만 not None
      reasoning: dict[str, str]                   # 전역 (current_price, balance 등)
  ```

  Invariants (`@model_validator`):
  - `skip_reason is not None ⇔ (len(sell_actions) == 0 AND buy_action is None)`
  - 매도 슬롯 번호 중복 금지 (`len(set(sa.slot_number for sa in sell_actions)) == len(sell_actions)`)
  - 매도 + 매수 슬롯 번호 충돌 금지 (같은 evaluation에서 슬롯 N을 팔고 동시 슬롯 N을 사는 일은 없음 — sells-then-buys 순서로 자연 보장)

- **DB schema 변경** (`SqliteDecisionRepo`):
  - 기존 `action TEXT` 컬럼 제거.
  - 신규 컬럼 `sell_actions_json TEXT NOT NULL DEFAULT '[]'`, `buy_action_json TEXT`, `skip_reason TEXT`.
  - JSON 직렬화는 Phase 0의 `PortfolioSnapshot.valuations_json` 패턴 그대로 (TypeAdapter).
  - **마이그레이션**: §3.4 정책에 따라 빈 DB로 시작. 자동 마이그레이션 코드 작성 안 함.

- **출력 호환성**:
  - `output_formatter.format_paper_decision`: 다중 액션 박스 표현으로 갱신 (예: `Sells: slot 2 (+12.3%) qty=18 px=33500 / Buys: slot 2 qty=15 px=29800`).
  - `BacktestResult.from_run` 의 `Counter(d.action for d in decisions)` 카운트 → `Counter(action_kind for d in decisions for action_kind in d._kinds())` 같은 헬퍼로 변경. `_kinds()`는 `["sell_slot_N" for sa in sells] + ["buy_split_M" if buy] + (["skip:..."] if skip)` 반환.
  - JSON 출력은 `Decision.model_dump_json()` 자동 적용 (구조화 그대로 노출).

- **이유**:
  - "한 날 1 Decision row" 패턴 유지 → 일별 회고/감사 추적이 단순.
  - 분할별 독립 매도(§2.1)의 reasoning을 슬롯 단위로 보존.
  - reasoning dict의 string-only 제약을 우회 (구조화 데이터를 dict 안 stringify로 욱여넣지 않음).
  - 결과적으로 `Decision`이 "하루의 모든 행동 단위"가 되어 의미가 더 명확.

- **블래스트 반경 (사전 식별)**:
  - `src/domain/models.py::Decision` (구조 변경) + `SellActionRecord` / `BuyActionRecord` 신규
  - `src/use_cases/daily_orchestrator.py` (Decision 생성 로직)
  - `src/infrastructure/repositories/sqlite_decision_repo.py` (schema)
  - `src/adapters/mock/in_memory_unit_of_work.py::InMemoryDecisionRepo` (호환)
  - `src/application/backtest_runner.py` (action counter)
  - `src/cli/output_formatter.py`
  - `tests/integration/test_backtest_paper_equivalence.py` (`_decision_keys` 산출 로직)

### 5.4.1 reasoning 필드 운영 정책

- 전역 `Decision.reasoning` 은 evaluation 시점의 컨텍스트 (current_price, balance, sell_strategy/buy_strategy 사용된 config 핵심 파라미터 등).
- per-action `SellActionRecord.reasoning` / `BuyActionRecord.reasoning` 은 해당 슬롯의 트리거 사유 (entry_price, profit_pct, trigger_price 산출 근거 등).
- CLAUDE.md §8.1 "모든 결정은 로그" 정신 그대로 — 6개월 뒤 디버그 가능 수준 유지.

### 5.5 MockBroker SELL 처리

- **결정**: `MockBroker.place_order(OrderSide.SELL)` 처리 신규.
  - 잔고에 cash 입금 (`+= filled_quantity * filled_price`)
  - 포지션 quantity 차감
  - simulate_partial_fill_rate / simulate_rejection_rate / simulate_timeout_rate 동일 적용 (대칭 로직)
  - 부분 매도 simulate는 ADR §2.4에 따라 **불허** — partial sell이 발생하면 broker 내부에서 reject로 변환할지 vs 도메인 무결성 위반으로 raise할지는 §5.6에서 결정.

### 5.6 부분 체결 매도 정책

- **결정**: MockBroker가 SELL을 partial로 시뮬레이션할 가능성을 **0
  (`simulate_partial_fill_rate=0`)** 로 강제. 부분 매도 도메인 모델
  자체가 없으므로 broker도 발생 시키지 말아야 안전.
- **구현**: `MockBroker.__init__`에 새 파라미터 `allow_partial_sell:
  bool = False` 추가. SELL 평가 시 `simulate_partial_fill_rate` 적용 전
  분기. Phase 1+에서 재고.
- **재검토**: Phase 1 KIS API에서 실제 부분 매도가 발생하면 별도 정책
  결정 (현재로선 SELL을 fully reject 후 다음 날 재시도 가정).

## 6. 설정 관리 확장 — YAML Layer 2 신규 구축 [범위 추가]

### 6.0 사전 인지 (사용자 합의 (가) 결정)

Phase 0 ADR §9 / CLAUDE.md §9에 박제된 "3계층 분리"는 Phase 0에서 Layer 1 (코드) + Layer 3 (CLI flag)만 구현된 상태. **Layer 2 (config/strategies.yaml)는 미구현**. Phase 0.5에서 D vs F 비교 자동화 핵심이 YAML 분리이므로 Layer 2 인프라도 함께 구축.

### 6.2 로더 + 검증

- **위치**: `src/infrastructure/yaml_strategy_config_loader.py`
- **함수**: `load_strategy_config(path: Path) -> dict[str, AssetStrategyBundle]`
  - `AssetStrategyBundle` (DomainModel): asset, buy_config, sell_config, reentry_config (모두 pydantic 검증).
- **검증**:
  - 누락 키 → ValidationError
  - 알 수 없는 strategy 이름 → ValueError
  - 파라미터 범위 (`profit_target_pct ∈ (0, 100)`, `cooldown_days ∈ [0, 365]`)
  - reentry_strategy 와 reentry_parameters 일관성:
    - `current_market` 인데 `cooldown_days` 명시 → warning (사용 안 됨)
    - `hybrid` 인데 `cooldown_days` 누락 → ValidationError
- **Phase 0.5 단일 자산 가정**: dict의 첫 키만 사용. 멀티 자산은 Phase 0.7.

### 6.3 CLI `--config` 옵션 (mutually exclusive 정책)

- **결정**: `trading backtest` / `trading paper` 양쪽에 `--config PATH`
  옵션 추가. `--config`와 **strategy 파라미터 flag**는 **mutually exclusive** — 동시에 지정 시 `click.UsageError` 로 즉시 거부.
- **strategy 파라미터 flag 정의** (거부 대상):
  - `--drop-pct`, `--max-split`, `--per-split-amount`, `--max-split-per-day`
  - (Phase 0.5 신규) `--profit-target-pct`, `--max-sells-per-day`, `--reentry-strategy`, `--cooldown-days`
- **메타 옵션 (함께 허용)**:
  - `--csv`, `--start`, `--end`, `--date`, `--db`, `--capital`, `--json`
  - 이유: 메타는 실행 환경 기술 (어디서/언제/얼마로). 전략 본질이 아님.
- **거부 메시지 예시**:
  ```
  Error: --config and strategy flags (--drop-pct, --max-split, ...) are mutually exclusive.
  Either pass --config PATH (recommended for reproducibility) or use the flag-only form.
  ```
- **이유**:
  - **명확성**: 같은 파라미터를 두 곳에서 지정하면 어느 게 우선인지 README 없이 알 수 없음.
  - **재현성**: 백테스트 결과 박제 시 "이 명령으로 재현"이 단순 — config 파일 + 메타 옵션만.
  - **Data Snooping 방지** (§6.5): flag 빠르게 바꿔가며 튜닝하는 유혹 차단. config 변경은 git diff 박제 동반.
  - **자동화 친화**: `trading backtest --config xxx.yaml` 한 줄로 모든 전략 파라미터 결정.
- **`--config` 미지정 + flag 사용 → Phase 0 호환 흐름 그대로** (regression 회피).
- **`trading config validate --config PATH`**: 신규 명령. 로더만 호출하여 검증 결과 출력 (실행은 안 함).

### 6.4 Hot reload 미도입 (재확인)

- Phase 0.5 미도입. 시스템 재시작이 설정 변경 적용 메커니즘.
- Phase 1 실거래 진입 후 검토.

### 6.5 Data Snooping 방지 재강조

YAML 파라미터가 5분 안에 변경 가능해지면서 무분별 튜닝 유혹 증가.
Phase 0 ADR (없으면 본 ADR §6.5에 박제) 정책 적용:
1. 파라미터 변경 전 **가설 명시** ("왜 이 값이 더 좋을 것 같은가?")
2. 한 번에 1~2개 변수만 변경
3. ADR에 변경 이유 박제
4. 결과 안 좋으면 원복. "혹시 더 잘 맞는 값" 무한 탐색 금지

Phase 0.5 백테스트는 D vs F 정책 비교가 핵심. 파라미터 (`profit_target_pct`,
`cooldown_days`, `drop_threshold_pct`) 튜닝은 별도 작업.

## 8. 백테스트 비교 계획

### 8.1 측정 지표

| 지표 | 산출 방법 | 의미 |
|---|---|---|
| Total return | `(final_value / initial - 1) × 100` | 절대 수익 |
| CAGR | metrics.cagr | 연 환산 |
| MDD | metrics.max_drawdown | 위험 |
| Sharpe | metrics.sharpe_ratio (rf=0) | 위험조정수익 |
| Calmar | metrics.calmar_ratio | CAGR/|MDD| |
| **자본 회전율 (신규)** | `누적 buy 금액 / initial_capital × (252 / N_days)` | 자본 활용 적극성 |
| **누적 매도 횟수 (신규)** | `count(action.startswith("sell_"))` | 익절 발화 빈도 |
| **평균 자본 활용률 (신규)** | `mean(committed_capital_t / initial_capital for t in days)` | 시간평균 자본 활용 |
